# 07 · 可靠性与验证

> 前六册讲的是"这个系统是怎么设计的"。本册回答两个更硬的问题：**你怎么知道它是对的**？以及**它到底在哪些地方不够好**？
>
> 这两件事在解读一个项目时价值最高，也最难自己补出来——因为设计文档会告诉你"我做了什么"，但只有**验证过程**和**已知缺陷**能告诉你"它是否真的成立"。
>
> 主要素材：[scripts/chaos_test.sh](../../scripts/chaos_test.sh)、[scripts/benchmark.sh](../../scripts/benchmark.sh)、[tests/](../../tests/)、[docs/安全审查报告.md](../安全审查报告.md)、[docs/性能压测报告.md](../性能压测报告.md)。

---

## 速览

1. **测试分四层，分层标准是"隔离"**：存储语义不依赖网络、Raft 一致性必须用真框架、Watch 逻辑分支多用单测穷举、HTTP 路由用真起服务验证。**为什么这么分**比"有多少个用例"重要。
2. **47 个用例里最关键的 2 个在 `raft_cas_test`**：它特意起了一个单节点 braft 组，而不是用单机实现——因为单机实现测不出"日志序保证并发原子"这件事。
3. **混沌测试用 4 个场景 + 2 个后台校验器**：kill Leader / kill Follower / 网络分区 / 重启追赶，同时有程序持续"写后立即读"和"校验事件 revision 严格递增"，**跑完违例数必须为 0**。
4. **最有价值的缺陷是混沌测试抓到的，不是读代码读出来的**：一个落后节点在追赶日志时会重放旧事件，导致订阅者收到重复、甚至 revision 回退的事件。
5. **代码审查用了 4 个并行只读的子代理**，从 Raft 核心、服务层、存储、前端四个维度审，发现约 38 项（来源说明见 5.1），选了 9 项修复。**其中两条高危项同源**——"写串行、读并行"这个假设没有被每条路径遵守；第三条（CORS）属于另一类问题。
6. **性能上的取舍是明写的**：为了修"节点假死"，等待原语换成 bthread 版本，代价是 4 核环境下吞吐降到约 1/3——**用吞吐换可用性，这是一个有意识的决定**。
7. **边界要说清楚**：无鉴权、无 TLS；`--raft_sync=false` 只用于压测；混沌校验器不是 Jepsen；`apply` 非幂等；以及一批**明确记录为"未修"**的已知缺口。

## 一、概念铺垫：分布式系统的验证手段

| 手段 | 能验证什么 | 不能验证什么 |
|---|---|---|
| 单元测试 | 模块内部的逻辑分支 | 跨模块、跨网络的真实时序 |
| 集成测试 | 多个模块组装后的行为（含真实的网络栈） | 故障场景 |
| 压力测试 | 吞吐上限、延迟分布、瓶颈在哪 | 正确性 |
| **故障注入 / 混沌测试** | **故障下的正确性（不丢、不乱序、能恢复）** | 性能 |
| 形式化验证 / 线性化检查器（如 Jepsen） | 严格的一致性判定 | 实现成本极高 |

**关键认知**：这几类手段验证的是**不同的东西**，不能互相替代。一个通过了全部单元测试、QPS 很高的系统，仍然可能在"Leader 被 kill 的瞬间"返回错误的数据——只有故障注入能发现这一类问题。

## 二、背景与目标

### S · 问题：什么才算"验证过了"

一个分布式系统要回答的验证问题至少有三层：

1. **功能对不对**：存进去的能取出来吗？版本号对吗？
2. **一致性能不能守住**：并发写下会不会出现两个都成功？广播出去的事件会不会乱序？
3. **故障下会怎样**：Leader 挂了、网络断了、节点重启了，系统还能正确工作吗？

第三层最容易被忽略，也最难靠"读代码"保证。

### T · 目标

- 每一个核心机制都有**对应的验证手段**——不是"跑了一遍看起来没问题"，而是"有一个能稳定复现失败场景的检查"。
- 关键结论要有**可追溯的原始数据**（环境、二进制指纹、完整输出）。
- 已知的不足要**明确记录**，并且区分"有意不做"和"没来得及做"。

## 三、验证体系

### 3.1 测试矩阵：47 个用例怎么分层

| 层 | 测试 | 用例数 | 验证什么 | **为什么不放在更上层测** |
|---|---|---|---|---|
| 存储语义 | `store_test` | 17 | MVCC 读写、revision/version 语义、CAS、Compaction、持久化 | 隔离底层正确性，避免被 Raft 的网络行为掩盖 |
| Raft 一致性 | `raft_cas_test` | 2 | 并发 CAS 在**真实 Raft** 下恰一个成功 | 需要真 braft；单机实现是同步直调，**测不出日志序保证的原子性** |
| Watch 语义 | `watch_test` | 15 | 重放、过滤、续传、背压、`COMPACTED` 判定 | 逻辑分支多，适合单测穷举 |
| HTTP 路由集成 | `http_test` | 13 | 真起服务：REST 分发、CORS、错误码、内置服务关闭、gRPC 共存 | 路由层原本零测试（审查发现的缺口），专门补上 |

**最值得说的是 `raft_cas_test` 的设计**：它没有用 `LocalNode`，而是起了一个**单节点 braft 组**（成员只填自己，多数派 = 1，自动选主）。文件头的注释写明了理由：

> `LocalNode::Apply` 直接同步调用存储层，**多线程并发调用会违反存储层的单写者约定**（构成数据竞争）；而单节点组仍会走完"提交 → `on_apply` 串行应用 → 比较-写入"的完整链路。

换句话说，**用 `LocalNode` 连"并发是否安全"都测不准，更别说证明"Raft 日志序保证原子性"了**。

这是"测试要测对层次"的一个好例子：**用错误的替身，测试会通过，但它什么都没证明。**

### 3.2 混沌测试：4 个场景

`scripts/chaos_test.sh` 会真的把节点杀掉、停住、重启：

| 场景 | 手法 | 验证什么 |
|---|---|---|
| A · kill Leader | `kill -9` | 集群自动重选；重选期间的瞬时写失败被视为可接受，恢复后读写正常、线性一致 |
| B · kill Follower | `kill -9` | 多数派仍在，读写正常 |
| C · 网络分区 | `kill -STOP` 后再 `-CONT` | 被隔离的节点不会造成双主或返回过期值 |
| D · 重启追赶 | 重启宕机节点 | 经日志/快照自动追平，Watch 补上断档 |

> **为什么用 `SIGSTOP` 模拟分区**：真正的网络分区要用 `iptables`，而它需要 root 权限。`SIGSTOP` 能让进程"心跳和请求都不可达"，效果上等价，且不需要特权。

### 3.3 两个校验器：怎么"断言"没出错

光有故障场景还不够，还需要**在故障期间持续断言正确性**。项目里有两个后台程序：

| 校验器 | 做什么 | 记什么违例 |
|---|---|---|
| **`verifier`** | 往一个固定 key 写入严格递增的序号（**key 不变，值递增**），然后**立刻读回来** | 读到空、或读到的值小于上次确认值 → `LINEAR_VIOLATION` |
| **`watch_verifier`** | 带 `from_revision` 持续长轮询续传，逐事件校验 | revision 不是严格递增（出现重复或回退）→ `WATCH_ORDER_VIOLATION` |

跑完全部场景后 grep 计数，**违例数为 0 脚本才算通过**。

> **诚实的边界**：这是"写后立即读"的**定向黑盒断言**，能抓住"读到旧值""revision 回退或重复"这类大问题。但要注意两点：
>
> 1. **它抓不到"事件缺失"**——`watch_verifier` 判的是"新 revision 是否大于上一个"，而事件中间出现空档仍然满足严格递增，不会被判为违例。
> 2. 它**不是** Jepsen/Knossos 那种记录全部并发历史、做严格线性化判定的工具——后者需要捕获所有操作的开始/结束时间并离线检查是否存在合法的线性化顺序。两者的严格程度不在一个量级上。

## 四、踩坑档案

以下每一条都真实发生过。按"现象 → 怀疑 → 定位 → 修复 → 验证"复述，这是本册最有价值的部分。

### 4.1 坑一：节点"假死"——标准库的同步原语阻塞了框架的线程

**现象**：高并发写压测下，节点"能 ping 通，但不再响应任何请求"。像死锁，但又不是。

**根因**：brpc 用的是 M:N 线程模型——`num_threads = 4` 指的是**底层内核线程**的数量，而请求跑在用户态线程（bthread）上。写请求需要**同步等待** `on_apply` 的结果，而当时的实现用的是 `std::condition_variable`。

阻塞在 `std::cv` 上会**占住底层的内核线程**。4 个并发写请求就能把 4 个内核线程全部占满——于是 `on_apply` 的回调和网络处理再也拿不到线程执行，**整个节点停摆**。

**试错记录**（这一段最能体现排查过程）：

| 尝试 | 结果 |
|---|---|
| 把 `num_threads` 从 4 调到 16 | ❌ **无效**——问题不在线程数量，而在线程被占住 |
| `bthread_usleep` 轮询 + 原子标志 | ⚠️ 稳定，但 QPS 只有约 2500——瓶颈变成 sleep/wakeup 的调度开销 |
| `bthread::butex`（futex 语义） | ❌ 单测直接崩溃——它在内核线程上下文挂起后无法被唤醒（唤醒只对 bthread 生效） |
| **`bthread::Mutex` + `bthread::ConditionVariable`** | ✅ 挂起 bthread、让出内核线程 |

**这是一个显式的取舍，不是纯粹的胜利**：在 4 核虚拟机上，换成 bthread 原语后 **2912 QPS**，而原来用 `std::cv` 是 **7813 QPS——慢了约 3 倍**。

为什么还是选它？因为**"节点假死"是正确性缺陷，而吞吐是性能问题**。而且配置中心的真实写并发远低于压测值。**稳定性优先于吞吐**——单看数字像是把性能改差了，但它消除的是一个正确性缺陷。

### 4.2 坑二：闭包被提前销毁——一个只在高压下才现形的 UAF

**现象**：关闭 fsync 后做高吞吐压测，出现段错误，崩溃栈在 `bthread_mutex_lock`。

**根因**：写路径需要等待 `on_apply` 的结果，等待的载体是一个回调闭包。但 braft 可能在 `node_->apply()` **还没有返回**的时候，就已经复制完成并调用了闭包——而闭包在自己的 `Run()` 里会 `delete this`。

于是等待侧出现竞态：它正准备访问闭包的成员，而闭包已经销毁了。

**定位过程**：

1. 先**排除内存问题**——观察各节点常驻内存稳定（约 33MB），不是 OOM；
2. 起 3 个带调试器的节点跑压测，拿到崩溃栈：`bthread_mutex_lock → RaftNode::Apply → DoPut`；
3. 由此确认是"等待时的对象生命周期"问题。

**修复**：把等待所需的状态（互斥量、条件变量、完成标记）从闭包里**拆出来，放进一个由 `shared_ptr` 管理的独立对象**。等待方持有这个 `shared_ptr`，闭包被提前销毁也不影响它安全地等待。

**关键认知**：这个 bug **在默认开启 fsync 时也一直存在**，只是被 fsync 拖慢、把竞态窗口掩盖了。**修好前一个 bug（假死）之后，它才暴露出来**——两个问题是递进的，不是并列的。

**调试经验**：用 `gdb -batch` 启动节点**可能不复现**——因为调试器改变了时序。这类竞态必须靠高吞吐压测来复现。

### 4.3 坑三：落后节点重放旧事件——混沌测试抓出来的

**现象**：混沌测试的校验器报 `WATCH_ORDER_VIOLATION`——同一条事件被返回了两次。加日志后抓到更严重的情况：一个 `from_revision=57` 的请求，返回的 `current_revision` 竟然是 9。

**根因**：一个被 kill 的节点重启后，本地状态远远落后。在它**追赶日志的过程中会重新应用历史日志**，而每次应用都会广播事件。此时如果有客户端带着 `from_revision=57` 连到这个还在追赶的节点，就会收到节点本地重放出来的 revision 10~57 的旧事件。

**定位**：先确认重放区间本身的边界逻辑是对的（排除重放代码的问题）→ 给校验器加详细日志重跑 → 抓到真实的响应内容 → 查节点日志确认"落后 → 追赶 → 重播"这条链路。

**修复**：进入重放/等待之前，**先等本节点追平到请求的 `from_revision`**（最多 5 秒）；追不上就返回 `INTERNAL`，让客户端稍后重试。

> 注意这里返回的 `current_revision` **可能小于请求的锚点**（因为它就是本节点当前的 revision，而能进这个分支恰恰说明本地落后）。客户端必须忽略它、保留自己的锚点——源码注释里"绝不返回低于 `from_revision` 的值"的说法并未兑现。详见第 05 册 3.7。

> **这个缺陷的价值在于它是怎么被发现的**：不是读代码读出来的，是**自动化故障注入跑出来的**。静态阅读很难想到"追赶期间会重播"这个时序。

### 4.4 坑四：前端的忙循环饿死了其他定时器

**现象**：打开 Dashboard 后，节点卡片永远是空的。

**根因**：前端的 Watch 循环在"集群没有写入"时，后端会**立即返回**一个空响应。而前端代码在拿到空响应后**没有让出时间片，直接进入下一轮请求**——微任务占满了事件循环，导致负责刷新节点状态的定时器**永远得不到执行**。

**修复**：Watch 循环每轮让出 200ms。

**教训**：**前端的长轮询必须考虑"快速返回"的场景**。服务端"立即返回"在它自己看来是正常的（没有事件当然立即返回），但对客户端的循环逻辑来说，这就是一个可能失控的输入。

### 4.5 坑五：fsync 是写路径的成本中心

这一条严格说不是"坑"，而是对性能瓶颈的定位结论（见第六节的实测数据）：

- 关闭 fsync 后，低并发（8 连接）吞吐能快 **8~10 倍**，高并发（64 连接）只快约 **2.8 倍**。
- **结论必须带并发度**——脱离并发度说"快 N 倍"会得出自相矛盾的结论。

更重要的是理解它的性质：**fsync 不是代码缺陷，而是 Raft"多数派持久化"这条承诺的物理代价**。压测关闭它是为了看吞吐上限，生产环境必须开启。

## 五、代码审查：一次系统性排查

### 5.1 方法

用 **4 个并行的只读子代理**，分别从 Raft 核心、服务层与协议、存储与 Watch、前端与测试四个维度审查代码，并对照所依赖的框架源码核实行为。发现约 38 项问题后**交叉验证**，只保留置信度高的。

> **数字口径**："约 38 项"来自项目的过程记录（含已修、未修、设计取舍与低优先项）。[docs/安全审查报告.md](../安全审查报告.md) 本身列的是 3 项 HIGH + 多项 MEDIUM，逐条枚举合计 37 项——两者相容，此处保留"约 38"并注明出处。

### 5.2 修复的 9 项

| 严重度 | 问题 | 根因 | 修复思路 |
|---|---|---|---|
| **HIGH** | 安装快照时与并发读/回收竞争 → **use-after-free** | `db_.reset()` 重建数据库时没有任何同步 | 引入 `shared_mutex`：重建持独占锁，其余持共享锁（第 06 册 3.4） |
| **HIGH** | 单机模式并发写 → **revision 重复** | 单机下没有 Raft 的串行保证，多线程并发调用写路径 | `LocalNode::Apply` 加锁串行 |
| **HIGH** | 通配 CORS `*` → 任意网页可跨站读写 | 服务无鉴权 + `Access-Control-Allow-Origin: *` | 收紧为"仅同主机回显 Origin" |
| MED | 快照的 revision 在一致性视图之外读取 → 跨节点编号发散 | 导出时数据与时钟分开读 | 在同一个 LevelDB snapshot 下读全部 |
| MED | 快照不含配置版本索引 → 新节点按版本读配置丢失 | 快照数据结构缺字段 | 增加 `cfg_kvs` 字段随快照导出/恢复 |
| MED | 层级 key 的历史查询跨 key 泄漏 | `cfg/` 前缀碰撞 | 遍历时校验记录内嵌 key（第 01 册 6.4） |
| MED | `meta/revision` 独立写 + 批次失败 → 状态发散 | 时钟与数据不在同一批次 | 改签名，强制并入同一批次（第 06 册 3.1） |
| MED | 空 key 污染命名空间 | 缺参数校验 | 新增错误码，写路径入口拒绝 |
| MED | 框架内置服务面板泄露运行参数 | 默认开启 | 关闭内置服务 |

### 5.3 三条高危项的共同病根

这是这次审查最有价值的发现。三条 HIGH **看起来毫不相关**（一个是快照、一个是单机并发、一个是 CORS），但前两条其实是同一个假设被打破：

> **存储层"写串行、读并行"的假设，没有被每一条路径遵守。**

- **快照路径**踩穿了 `db_` 的**生命周期**——`LoadSnapshot` 重建数据库时，假设"没有别人在用"；
- **单机模式的写路径**踩穿了"**只有 `on_apply` 是串行的**"这个前提——单机模式下没有 `on_apply`，多线程直接调了写；
- **CORS** 那一项是另一类问题（"零鉴权 + 通配 CORS"叠加出安全边界缺失），但它同样说明：**边界假设没有被显式地写下来并逐条检查**。

**这个洞察比修复本身更有意义**：一个隐含的架构假设，如果没有在代码里显式声明，就会在不同的路径上被悄悄违反。

### 5.4 发现但**没有修**的问题

这一节很重要——**把"有意不做"和"没来得及做"分开**。

**明确选择的取舍（不是缺陷）**：

| 项 | 说明 |
|---|---|
| Watch 背压时直接断开慢消费者 | 这是设计（第 05 册 3.6），不是 bug |
| `compact_rev` 是全局水位，会保守误报 | 实现简单性的取舍（第 06 册 6.2） |
| Compaction 全量扫描 + 逻辑删除 | 在配置中心的数据量级下可接受 |
| Admin 只能走 HTTP | brpc restful 映射的结果，运维面够用（第 02 册 4.3） |

**已知但未修的缺口**：

| 项 | 影响 | 修复思路（已有，未实施） |
|---|---|---|
| **无鉴权 + `/addpeer` 暴露** | 任何人可调成员变更，能让 Leader 把完整快照复制给攻击者地址 =**数据外泄通道** | 加令牌或 IP 白名单 |
| **`on_apply` 非幂等** | 节点在两次快照之间崩溃重启时，已应用的下标**只存在内存里**，重启后会从头重放 → 该节点 revision / version 递增两遍，与其他副本**永久漂移** | 在存储的同一批次里持久化"已应用到哪"，重放时跳过 |
| **Watch 断连释放延迟** | 客户端断开后，最长可能滞留 60 秒才释放 | 更频繁地检查连接状态 |
| **HTTP key 的百分号编码跨协议不一致** | 框架不对 URL 路径做百分号解码，同一个 key 在 HTTP 与 gRPC 下身份分裂 | 在入口显式解码 |
| **`kLeaseWaitMs` 恰好等于默认选举超时** | 边界情况下可能误报 `INTERNAL` | 把等待上限调得比选举超时略大 |

**还有一批低优先级项**（记录在案）：key 保留名冲突（第 01 册 6.3 的 `batch`/`cas`）、参数解析对垃圾输入过于宽松、`DecodeOrd` 对脏数据会抛异常等。

> **为什么要把这一节写出来**：一个项目的可信度，很大程度上取决于**它对自己边界的认识是否诚实**。如实列出已知问题，比宣称"没有问题"更有参考价值。

## 六、性能实测

### 6.1 环境与口径

> **环境**：阿里云云主机 · 8 vCPU / 16G / NVMe SSD / Ubuntu 22.04 · 多节点进程**同机环回** · 压测工具 ghz（gRPC）+ wrk（HTTP）· 每项 10 秒
> **口径**：代码加固之后的版本；`QPS / P99(ms)`

### 6.2 数据

| 场景 | 单机 | 3 节点·默认持久化 | 3 节点·关 fsync | 5 节点·默认持久化 | 5 节点·关 fsync |
|---|---|---|---|---|---|
| gRPC 写 Put ×8 | 28.7k / 0.6 | 1.8k / 10.3 | 15.9k / 1.4 | 1.2k / 11.0 | 13.0k / 1.7 |
| gRPC 写 Put ×64 | 41.8k / 3.1 | **10.0k / 11.6** | 28.2k / 4.7 | 7.4k / 14.7 | 24.4k / 5.8 |
| gRPC 写 Put ×128 | 38.1k / 6.1 | 16.0k / 13.0 | 31.0k / 7.1 | 12.6k / 18.9 | 27.3k / 8.8 |
| gRPC 读 Get ×64 | 38.6k / 3.6 | 45.2k / 2.8 | 42.5k / 3.3 | 44.1k / 3.0 | 40.5k / 4.1 |
| HTTP 读 GET | 259k / 3.6 | **275k / 0.5** | 271k / 0.5 | 267k / 0.5 | 263k / 0.5 |
| HTTP 写 POST | 102k / 81 | 17.9k / 12.6 | 75.4k / 4.2 | 13.0k / 15.5 | 50.4k / 1330 |

### 6.3 四条结论

1. **读远高于写**（HTTP 读 27 万 vs 写 1.2k~31k），符合配置中心"读多写少"的业务形态。
2. **Raft 复制的规模代价**：5 节点写吞吐比 3 节点低 **约 12%~33%**（随并发档位变化；多数派从 2/3 变成 3/5），而读路径几乎不受影响（Lease 本地读）。代价换来的是容错能力从"容忍 1 个故障"提升到"容忍 2 个"。
3. **fsync 是写路径的最大开销**：默认持久化 vs 关 fsync，**低并发（8 连接）相差 8~10 倍**，高并发（×64）只差约 2.8 倍、×128 约 1.9 倍。**说倍数必须带并发度**。
4. **加固没有带来性能回退**：加了 `shared_mutex` 之后同环境复测完整矩阵，**集群写路径没有任何一项变慢**（最大单格 +7%，是变快），读路径完全不受影响。

> **单机列的口径说明**：单机两格（HTTP 读/写）的 P99 取自 fsync=true 那一轮，数值偏大（3.6ms / 81ms）——这是**同机压测时 CPU 资源竞争产生的长尾噪音**，与读路径本身无关（fsync=false 轮次同项恢复到 0.44ms / 47ms）。QPS 稳定。README 的性能表对这两格标注了 `†` 说明同一情况。
>
> 原始证据存档在 [docs/压测结果_云主机_20260820.txt](../压测结果_云主机_20260820.txt)，含环境指纹、二进制 md5 与 3/5 节点的完整输出。

### 6.4 两个更有信息量的对照

| 对照 | 数字 | 说明了什么 |
|---|---|---|
| 修复前（`std::cv`） vs 修复后（bthread 原语） | 7813 vs 2912 QPS（4 核 VM） | **用约 2/3 的吞吐换掉了"节点假死"这个正确性缺陷** |
| fsync 开 vs 关 | 2912 vs 6452 QPS | **Raft 的持久性承诺是有实际价格的** |

## 七、通用知识

**测试设计**
- 分层测试的核心问题是"**这一层能不能测出这个东西**"。用错了替身，测试会通过，但什么也没证明。
- 单元测试适合"分支多、判定复杂"的逻辑；集成测试适合"组装后的行为"；**故障下的正确性只能靠故障注入**。
- 校验器的严格程度要如实说明——"写后立即读"和"完整的线性化检查"不是一个量级的东西。

**排查方法论**
- **竞态用压力复现，别指望单步调试**——调试器本身会改变时序。
- 先**排除最简单的原因**（比如内存耗尽），再深入。
- 修复一个 bug 之后要重新压测——**它可能只是掩盖了下一个 bug**。
- 每个修复都配一个"能稳定复现原问题的黑盒操作"，否则无法证明真的修好了。

**性能分析**
- 报性能数字必须带**环境、工具、并发度、口径**。脱离这些的数字没有意义，甚至互相矛盾。
- 性能优化往往有代价，**"变快了"和"变好了"不是一回事**——这个项目的几次优化都是明确的取舍。
- 定位瓶颈时要问"**这个开销是什么承诺的代价**"——fsync 不是缺陷，是持久性的价格。

**工程判断**
- 一个隐含的架构假设如果没有被显式声明，就会在不同的路径上被悄悄违反。**审查时最有价值的发现往往是"同一个病根的多处表现"**。
- 诚实地列出"已知未修的问题"，比宣称"没有问题"更能建立信任。
