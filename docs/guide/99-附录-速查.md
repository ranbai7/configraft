## 一、术语表

### 项目概念

| 术语 | 含义 | 详见 |
|---|---|---|
| **ConfigNode** | 服务层唯一依赖的抽象接口，15 个方法，有单机与集群两个实现 | 02 册 |
| **LocalNode** | 单机实现，加锁后直接同步调 Store | 02 册 |
| **RaftNode** | 集群实现，写经 braft 复制日志，读走 Lease 校验 | 02/03 册 |
| **RaftCmd** | 写进复制日志的内部指令（`oneof` 六选一），与对外 API 分离 | 01 册 |
| **revision** | **全局**逻辑时钟，每写 +1，跨 key 单调；MVCC / Watch / CAS 的共同锚点 | 01 册 |
| **version** | **单个 key** 的修改序号，从 1 起；删除也计一次 | 01 册 |
| **tombstone** | 墓碑：删除时写 `deleted=true` 的记录而不真删 | 01/06 册 |
| **WatchHub** | 每进程一个的事件分发中枢，解耦事件的产生与消费 | 05 册 |
| **Waiter** | 一次长轮询会话；Hub 存 `weak_ptr`，强引用在等待线程手里 | 05 册 |
| **锚点 / `current_revision`** | 客户端下一次请求的 `from_revision`；有事件时取最后一条事件的 revision | 05 册 |
| **背压** | 订阅者缓冲满（1024 条）即断开，绝不让它阻塞写路径 | 05 册 |
| **compact_rev** | Compaction 已回收的最大 revision（水位线），Watch 据此判定 `COMPACTED` | 06 册 |

### 分布式共识

| 术语 | 含义 |
|---|---|
| **复制状态机（SMR）** | 相同初始状态 + 相同输入序列 + 确定性状态机 = 各副本状态一致 |
| **多数派（quorum）** | 超过半数的节点；任意两个多数派必然相交，这是杜绝双主的数学基础 |
| **term（任期）** | 单调递增的"第几届领导"编号 |
| **commit（提交）** | 日志被多数派确认，此后不会被撤销 |
| **apply（应用）** | 日志被真正执行到状态机，产生可见的状态变化 |
| **pre-vote（预投票）** | 候选人用假想任期试探，拿到多数派同意才真正升任期 |
| **Leader Lease** | 给读用的凭证：有效期内可确认"我仍是唯一 Leader"，时长 1000ms |
| **Follower Lease** | 给投票用的承诺：有效期内不参与选举，时长 2000ms |
| **Leader 完备性** | 某条日志一旦提交，之后所有任期的 Leader 都必然包含它 |

### 存储与数据

| 术语 | 含义 |
|---|---|
| **LSM-Tree** | 用顺序写替代随机写的存储结构；LevelDB 的实现基础 |
| **MVCC** | 多版本并发控制：写不覆盖旧值，产生新版本 |
| **Compaction（本项目）** | **回收 MVCC 历史版本**（每 key 保留最近 10 个） |
| **Compaction（LevelDB）** | 存储引擎内部合并 SSTable 的机制，与本项目同名但无关 |
| **WriteBatch** | 一批写操作，原子提交（要么全生效要么全不生效） |
| **前缀扫描** | 利用 key 有序性做范围遍历，是这类存储的主要查询模式 |
| **`*Locked` 约定** | 私有方法后缀，表示"调用方已持锁，内部不得再加锁" |

### 服务端与并发

| 术语 | 含义 |
|---|---|
| **bthread** | brpc 的用户态线程；阻塞它会占住底层内核线程 |
| **M:N 线程模型** | 大量用户态线程映射到少量内核线程；`num_threads` 指后者 |
| **长轮询** | 请求发出后服务端挂起不返回，有事件才返回、或超时返回空 |
| **单端口多协议** | 同一监听端口承载 gRPC、HTTP、集群内部通信三路流量 |
| **restful 映射** | 把 URL 路径挂到 RPC 方法上，使其可用普通 HTTP 触发 |
| **CORS** | 跨源资源共享；本项目只回显同主机 Origin，不用通配符 |

## 二、错误码

| 值 | 名称 | 语义 | 客户端应该做什么 |
|---|---|---|---|
| 0 | `OK` | 成功 | — |
| 1 | `KEY_NOT_FOUND` | key 不存在（含已删除） | 按业务处理 |
| 2 | `CAS_FAILED` | CAS 期望值不匹配 | 重新读取当前值后决定 |
| 3 | `NOT_LEADER` | 写请求落到了非 Leader（响应 message 含 Leader 地址） | **向新地址重发** |
| 4 | `VERSION_NOT_FOUND` | 指定的配置版本不存在 | 查一下历史版本列表 |
| 5 | `COMPACTED` | 请求的 revision 之前的历史已被回收（响应含 `current_revision`） | **从新锚点重新开始** |
| 6 | `INVALID_ARGUMENT` | 参数非法（如空 key） | 修正请求 |
| 100 | `INTERNAL` | 内部错误；也包括"本地未追平""缓冲溢出""lease 未就绪"等需重试的情况 | **稍后重试**（Watch 类的 INTERNAL 响应会带 `current_revision`，可用于续传；读/写路径的 INTERNAL 没有这个字段） |

> `VERSION_NOT_FOUND`(4) 与 `COMPACTED`(5) 必须分开：前者是"单个 key 的某个版本不存在"，后者是"全局 revision 区段被回收"，客户端的反应完全不同。

## 五、知识点索引（按能力轴）

把本套资料里**脱离本项目仍然成立**的知识点，按能力轴重新归纳。每条后面是从哪一册展开的。

### 分布式共识

- 复制状态机（SMR）是分布式一致性的通用蓝图；前提是状态机必须确定性 — 03 册
- 多数派相交性是"同一时刻最多一个 Leader"的数学基础 — 03 册
- 任期（term）是拒绝过期请求的通用手段 — 03 册
- pre-vote 用于避免被隔离节点反复推翻健康 Leader — 03 册
- Raft 的两个安全性保证：Leader 完备性、状态机安全 — 03 册
- "提交"与"应用"之间的间隔是所有异步问题的来源 — 03 册
- 共识的持久化代价最终落在 fsync 上 — 03/07 册

### 一致性模型

- 线性一致：读到的结果表现得像只有一份数据，且与真实时间相容 — 04 册
- 线性一致与服务端可串行化是两个正交的维度 — 04 册
- 顺序一致只要求"顺序相同"，不要求与真实时间相容 — 04 册
- 最终一致只承诺收敛，不承诺何时 — 04 册
- 一致读的两条路线：ReadIndex（无时钟假设、每次读多一轮往返）vs Lease（有时钟假设、零额外往返）— 04 册
- 区分"自认为的状态"与"客观状态"需要外部证据，不能靠自省 — 04 册

### 数据模型与存储

- 有序 KV 中"把什么字段放在 key 前面"决定了数据按什么聚类 — 01 册
- 数值要参与排序就必须编码成定长字符串 — 01 册
- MVCC 用"写新版本"代替覆盖，代价是需要回收机制 — 01/06 册
- 回收会破坏历史完整性，因此需要水位标记 — 06 册
- 水位是全局还是 per-key 是明确的取舍：全局简单但保守误报 — 06 册
- 批量写内部读不到自己未提交的写 — 06 册
- 有依赖关系的写必须放进同一个批次（包括计数器的推进）— 06 册
- append-only 的复制日志与"就地删除"天然冲突，删除通常表达成追加记录 — 01 册
- 前缀命名空间的固有风险：被编码字段若含分隔符，前缀就不再是可靠边界 — 01 册

### 并发与生命周期

- 用户态线程模型下，阻塞式等待会占住内核线程；同步原语必须与线程模型匹配 — 03/07 册
- 异步回调可能早于调用方准备好时执行，甚至被销毁 — 03 册
- 用独立对象 + 智能指针把"等待信号"与回调对象的生命周期解耦 — 03 册
- `shared_mutex` 保护的是资源生命周期，不只是数据读写 — 06 册
- 不可重入的锁需要明确的"谁负责加锁"约定（如 `*Locked` 命名）— 06 册
- 锁序必须全局一致，一处反转就构成 ABBA 死锁 — 05 册
- 对象所有权要回答"谁决定它什么时候销毁"：独占用 `unique_ptr`、共享用 `shared_ptr`、借用的用裸指针或 `weak_ptr` — 02 册

### 网络与服务端

- 长轮询是用"故意不返回的请求"模拟服务端主动推送 — 05 册
- 单端口多协议靠框架按协议特征分流，简化运维 — 02 册
- 路由能力受框架限制；框架不支持的，就得在业务层补一层分发 — 02 册
- URL 保留字会成为隐藏的语义冲突（key 撞上路由关键字）— 01 册

### 消息与推送

- 断点续传的锚点必须是"已确认送达的位置"，不能是"生产者当前位置" — 05 册
- "先订阅、后补历史"的顺序决定会不会漏消息；代价通常是可以重复但不能漏 — 05 册
- 背压必须"断开"而不是"等待"，否则慢消费者会成为系统单点 — 05 册
- 用 `weak_ptr` 让广播方"尝试投递、失败即跳过" — 05 册

### 可靠性工程

- 分层测试的核心是"这一层能不能测出这个性质"；用错替身等于没测 — 07 册
- 故障下的正确性只能靠故障注入，静态阅读发现不了 — 07 册
- 竞态用压力复现，别指望单步调试（调试器会改变时序）— 07 册
- 修复一个 bug 后要重新压测，它可能只是掩盖了下一个 — 07 册
- 性能数字必须带环境、工具、并发度、口径 — 07 册
- 隐含的架构假设若未显式声明，会在不同路径上被悄悄违反 — 07 册
- 诚实列出"已知未修"比宣称"没有问题"更能建立信任 — 07 册
