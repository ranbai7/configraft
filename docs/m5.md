# M5：CAS 原子更新 + 线性一致读

> 配套：`开发计划.md` M5 章节。本文记录设计决策与实现要点，是对面试官"一致性到底怎么保证"的应答素材。

## 一句话定位

- **CAS**：`CompareAndSwap(key, expect, value)` 作为一条 Raft 指令提交，`on_apply` 串行"比较-写入"，原子性天然成立——并发 CAS 恰一个成功。
- **线性一致读**：读路径接入 braft 的 **leader lease**，保证"发布后立即读必得新值、leader 变更后读不读到过期配置"。

## CAS：原子性来自 Raft 串行 apply

### 设计

```
客户端 CompareAndSwap(key, expect, value)
   └─ RaftCmd{CAS, key, expect, value}  ──braft 复制──▶ on_apply 串行执行:
                                                       Store::CompareAndSwap(key, expect, value)
                                                         └─ ReadMain(key) 读当前值
                                                         └─ expect 匹配? ──否──▶ CAS_FAILED（不消耗 revision）
                                                         └─ 匹配 ──▶ 分配新 revision，写主索引+历史
```

### 语义表（expect 空串 = 期望 key 不存在，含 tombstone）

| 当前状态 | expect="" | expect="v" |
|---|---|---|
| 不存在 / tombstone | ✅ 成功（重建） | ❌ CAS_FAILED |
| 存在、值="v" | ❌ CAS_FAILED | ✅ 成功 |
| 存在、值="" | ❌ CAS_FAILED（歧义：空 expect 无法表达"期望值为空串"） | ✅ |

### 面试要点：CAS 原子性来源

1. **读-比较-写整体是一条 Raft 指令**：不会出现"读旧值→被并发改→写覆盖"的竞态——因为所有写都经 Raft 串行 apply，CAS 的比较和写入在同一串行点上原子完成。
2. **失败不消耗 revision**：先比较后 `NextRevision()`，CAS_FAILED 不推进全局逻辑时钟（避免无谓的 Watch 事件和存储膨胀）。
3. **单测证明**：单节点 braft 组 16 线程并发 CAS 同 key 同 expect → 恰 1 个 OK、其余 CAS_FAILED，终值 = 胜者值（`tests/raft_cas_test.cpp`）。

## 线性一致读：基于 leader lease（而非 ReadIndex）

### 为什么不用 ReadIndex？

**braft v1.1.2 没有 read_index API**（全量源码搜索确认）。自造 ReadIndex 需要改 vendored 共识核心（协议级改动，所有节点同步升级），网络不稳、依赖锁定的环境下风险高。braft 提供了官方测试覆盖的 **leader lease**，开 flag + 读路径封装即可。

### lease 正确性论证（面试核心）

`LEASE_VALID ⟹ 本地状态机包含所有已提交写`，承重墙是 **braft 的配置条目 = Raft 的 no-op**：

1. **Leader Completeness**：新 leader 日志包含所有已提交条目（选举 up-to-date 检查保证）。
2. **配置条目 = no-op**：`become_leader` 追加本任期第一条配置日志，其提交把 commit_index 一次推到 `last_log_index+1`，覆盖其下所有先前任期的已提交条目。
3. **lease VALID ⟹ 配置条目已提交**：`leader_lease_start` 只在配置条目提交后的 `ConfigurationChangeDone::Run` 执行，lease 才从 NOT_READY 转 VALID。
4. **`applied ≥ commit` 屏障**：状态机异步 apply，known_applied_index 滞后 committed_index；等待追平后本地 store 才反映到 commit 为止的所有写。

**论证链**：`LEASE_VALID` ⟹ 配置条目已提交 ⟹ commit 覆盖先前任期 ⟹ Leader Completeness ⟹ `applied≥commit` 后本地读反映所有已提交写 ⟹ lease 窗口内无新 leader ⟹ **线性一致**。

> **坑提醒**：`WaitAppliedCatchUp` 是必要条件但不充分——充分性靠第 3 步（no-op 配置条目）。若砍掉它回到"leader 直接读"，就是 M5 要修掉的旧缺陷。

### ReadIndex vs Lease（面试对比）

| 维度 | ReadIndex | Leader lease（本项目） |
|---|---|---|
| 机制 | 每次读向多数派发 quorum 探测 | 复用周期性 heartbeat ack 作为持续证明 |
| 安全前提 | 仅 Raft，无时钟假设 | 需所有 peer 开 flag + 一致 timeout + 时钟漂移有界 |
| 稳态读时延 | 每次 +1 quorum RTT | 本地 lease 检查，≈0 额外 RTT |
| 对 follower 负载 | 每次读扇出 RPC | 零额外负载 |

**口径**：configraft 是读时延敏感的配置中心，lease 用 heartbeat 摊薄探测成本；braft 恰不提供 read_index。我们用 lease 并在读路径补足弱假设：① 强制开 flag ② `applied≥commit` 屏障 ③ NOT_READY 有界等待。

### 读路径实现细节

```
Get(key, serializable=false):
  1. WaitLeaderLease(1s)   # LEASE_VALID→通过；NOT_READY 内部分自旋；超时/EXPIRED→失败
  2. WaitAppliedCatchUp(1s) # 单次 get_status 采样，applied ≥ committed
  3. 本地 store->Get(key)
Get(key, serializable=true):
  任意节点本地读（降级：最终一致，可容忍过期）
```

- **NOT_READY 短暂窗口**（刚选举，约 1 RTT）：内部分自旋吸收瞬态；超时返回 INTERNAL "leader not ready, retry"，**绝不填 LeaderId() 自我重定向**（否则客户端被引导回自己形成死循环）。
- **applied/commit 单次采样**：避免读到较新 applied + 较旧 commit 误判已追上。
- **降级读**：`serializable=true` 允许 Follower 本地读，用于可容忍过期的场景（如展示型监控）。

## 一致性概念辨析（面试）

- **Linearizable（线性一致）**：每个读看到"某个时刻"的完整状态，操作像在时间轴上单点发生——本项目的 `Get(serializable=false)`。
- **Serializable（可串行化）**：事务并发等价于某串行顺序——本项目无多键事务，单键 CAS 天然满足。
- **顺序一致（Sequential）**：单客户端视角符合程序顺序，但不同客户端可能看到不同顺序——`serializable=true` 降级读。
- **最终一致**：无收敛时间保证——本项目的 follower 本地读在无写入时收敛于 leader。

## 实测验证（2026-08-12）

3 节点集群（`scripts/run_cluster.sh`）：

```bash
# CAS 成功
curl -X POST 127.0.0.1:8003/v1/kv/foo/cas -d '{"expect":"old","value":"new"}'
# {"kv":{"key":"foo","value":"new","version":2,"revision":N}}

# CAS 失败（expect 不匹配）
# {"code":2,"message":"expect value mismatch"}

# 并发 CAS（多进程同 key 同 expect）→ 恰一个 "code":0，其余 code:2

# 线性一致读：Publish 后立即 Get(serializable=false) 必得新值
# leader 变更后：新 leader 上 Get 可见此前已提交的写
```
