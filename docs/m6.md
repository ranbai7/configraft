# M6：运维与发布 —— 成员变更 + 健康检查 + Docker 一键集群

> 配套：`开发计划.md` M6 章节。本文记录设计决策与实现要点，是对面试官"扩容怎么做、怎么保证安全"的应答素材。

## 一句话定位

- **成员变更**：基于 braft 的 `add_peer/remove_peer` 实现在线扩容/缩容，新节点先追平数据再进配置；移除 Leader 自动让位重新选主。
- **健康检查**：`GET /healthz` 暴露集群状态（role/term/commit/applied/leader/peers），供负载均衡与编排层探活。
- **Docker 部署**：`docker compose up` 一条命令起 3 节点集群，healthcheck 用 `/healthz`。

## 成员变更：braft 的 add_peer/remove_peer

### 接口封装（同步语义）

braft 的 `add_peer/remove_peer` 是异步接口（`Closure* done` 在 bthread 中回调）。RaftNode 用条件变量封装成同步调用：

```
AddPeer(peer)
  └─ 校验：IsLeader?（非 leader → NOT_LEADER + 重定向地址）；peer 地址合法?
  └─ node_->add_peer(peer, new ConfChangeClosure(outcome))   // 异步提交
  └─ cv.wait_for(60s)   // 同步等待 done
       ├─ 成功 → done->status() ok
       ├─ 失败 → EPERM(非 leader) / EBUSY(并发变更) / ECATCHUP(新节点追不上)
       └─ 超时 → 返回"可能仍在进行"，提示稍后查 health（不能撤销）
```

**关键设计**：`ConfChangeClosure` 的结果缓冲用 `shared_ptr`（而非裸指针）——若同步等待 60s 超时先返回，closure 仍存活，将来 `Run()` 写入 shared_ptr 安全，不会悬垂访问栈变量。

### braft 内部：单增删 vs joint consensus（面试重点）

```
ConfigurationCtx::start
  └─ STAGE_CATCHING_UP：对新 peer 启动 replicator 并 wait_caughtup（追平到 catchup_margin）
  └─ 单成员变更（nchanges==1）→ 跳过 joint，直接 STAGE_STABLE（兼容 legacy 单阶段）
  └─ 多成员变更（change_peers，nchanges>1）→ STAGE_JOINT（joint consensus）→ STAGE_STABLE
  └─ STAGE_STABLE：提交配置日志；若本节点被移除 → step_down(ELEADERREMOVED) 让位
```

- **单增删（single-server change）**：一次只改一个成员，配置日志像普通日志一样提交，多数派同意即生效。简单、工程上常用。
- **joint consensus（联合共识）**：一次变更多个成员时，先切到"新旧配置联合"的过渡配置（两个配置都必须多数派提交），再切到新配置。保证任意时刻安全性。
- braft 对单成员变更跳过 joint 是性能优化（少一轮提交），且已被证明安全。

### 为什么扩容先要追数据（面试必答）

`add_peer` 的 catchup 阶段**必须先让新节点追平数据，才提交配置变更日志**。原因：

1. 新节点带着落后日志进入配置后，一旦被选为 leader，它会覆盖提交"缺失的旧日志"，可能覆盖已提交数据——破坏安全性。
2. 追平（含快照 InstallSnapshot）保证新节点从配置生效起就有完整状态，能正确参与投票。
3. 追不上（超过 catchup_timeout）则整个变更失败，配置不变，集群不受影响。

**实测证据**：全新 node5 加入时，leader 发送 `InstallSnapshotRequest last_included_index=8`，node5 `snapshot loaded` 后再以日志追平到 index 39——数据无停机补齐。

### 网络分区下成员变更行为（面试答）

配置变更是一条复制日志，需多数派提交：
- Leader 在**多数派侧**：变更正常提交；分区恢复后新成员正常服役。
- Leader 在**少数派侧**：配置日志无法提交，变更阻塞直至 catchup 超时失败或 Leader 因失去多数派让位——配置不产生部分提交，安全。

## 健康检查 /healthz

- **为什么不是 /health**：brpc 1.17 内置 HealthService（短名 `health`）占用该路径；restful 映射的路径首段会被注册为 service 短名，`/health` 直接与内置服务冲突导致 Server 启动失败。改用 `/healthz`（k8s liveness 惯例）。
- **语义**：HTTP 200 = 进程 + 服务存活；响应携带 `role/term/commit_index/applied_index/leader_id/peers`，调用方用 `role=leader && applied≥commit` 判定"完全就绪"（与 M5 线性一致读屏障同一套指标）。
- **gRPC 与 REST 双协议**：同一 AdminService 同时暴露 `/configraft.v1.AdminService/GetHealth`（gRPC）与 `/healthz`（REST，JSON body 经 brpc `allow_http_body_to_pb` 自动解析）。

## Docker Compose 一键部署

```
docker compose up -d --build
  ├─ 3 容器同网络，固定 IP 172.28.0.11/12/13
  ├─ peers = 172.28.0.11:8001,172.28.0.12:8002,172.28.0.13:8003
  ├─ healthcheck 每 5s 探测 /healthz
  └─ 数据卷持久化 LevelDB + braft 元数据
```

### 部署踩坑（面试可讲）

| 坑 | 原因 | 解法 |
|---|---|---|
| docker.io 拉镜像失败 | 网络不可达 registry-1.docker.io | `FROM docker.m.daocloud.io/library/ubuntu:22.04`（镜像加速器） |
| `--listen_ip=node1` 解析失败 | `butil::str2endpoint` 只支持 IP 字面量，不支持 hostname | compose 网络 ipam 分配固定 IP，peers 用 IP |
| `/health` 启动冲突 | brpc 内置 HealthService 短名占用 | 用 `/healthz` |
| 镜像需携带依赖 | configraft_server 动态链接自构建的 `libbraft.so` | Dockerfile `COPY third_party/install/lib/libbraft.so` + `LD_LIBRARY_PATH` |

| 场景 | 结果 |

| RemovePeer 移除 leader 自身 | ✅ 让位为 follower，其他节点自动重选主（term+1） |

| 无效 peer 地址 | ✅ INTERNAL |
| 单机模式 addpeer | ✅ "single-node mode does not support membership change" |
| Docker 3 节点（compose up） | ✅ 3 容器 healthy，选举出 leader，follower 写重定向，读写正常 |
