# M7：测试、压测、混沌与优化

> 配套：`开发计划.md` M7 章节。本文记录压测报告、混沌测试方法与发现、性能优化与权衡，是对面试官"怎么验证正确性、压测指标怎么看"的应答素材。

## 一句话定位

- **混沌测试**：`scripts/chaos_test.sh` 对 3 节点集群执行 kill Leader / kill Follower / 网络分区（STOP）/ 重启，全程一致性验证（写线性一致 + Watch 有序不丢 + 自动恢复），**发现并修复了一个 Watch 边界 bug**。
- **压测**：ghz（gRPC）/ wrk（HTTP）测量 QPS 与 P99；**定位写路径最大热点 = braft 日志 fsync**。
- **优化**：修复高并发写路径节点假死/崩溃（同步等待改用 bthread 原语）。

## 压测报告（3 节点集群，4 核 VM，默认 `FLAGS_raft_sync=true`）

工具：ghz（gRPC，go1.23 编译）/ wrk（HTTP）。方法：压测写打到 leader，10s 时长。

| 场景 | QPS | P50 | P99 |
|---|---|---|---|
| 单机 gRPC Put (c8) | 9755 | 0.51ms | 3.37ms |
| 集群 gRPC Put (c8，优化前 std::cv) | 7813 | 0.47ms | 2.48ms |
| 集群 gRPC Put (c8，优化后 bthread cv) | 2912 | 2.46ms | 5.03ms |
| 集群 gRPC Put (c64) | 22491 | 1.55ms | 6.81ms |
| 集群 HTTP GET (wrk, c64) | 110k | 0.58ms | — |
| 集群 HTTP POST (wrk, c64) | 104k | 0.59ms | — |

**指标解读（面试）**：
- **QPS** = 每秒完成请求数，反映吞吐；**P99** = 99% 请求在阈值内完成，反映尾部延迟（比平均更真实，掩盖长尾）。
- wrk 比 ghz 高是并发差异（64 vs 8）+ HTTP 读路径无 Raft 写。
- 单机（LocalNode）9755 是"裸存储"上限；集群 7813 含 Raft 复制开销（约 -20%）。

## 性能优化：两个真实发现

### 发现 1：写路径同步等待用 std::cv 占满 worker → 节点假死（已修复）

ghz 高并发（c8/c16/c64）写路径复现：`RaftNode::Apply` 用 `std::condition_variable` 做同步等待，**bthread 阻塞 std::cv 会占住 pthread worker**（`num_threads=4`），并发写把 worker 占满 → 心跳/复制无 worker → 节点假死（进程在但无响应）或崩溃。

**修复**（commit eac5438）：`ApplyClosure` 改用 `bthread::Mutex + bthread::ConditionVariable`——wait 挂起当前 bthread、释放 worker；等待状态（`WaitState`）独立为 shared_ptr，消除 Run() 中 `delete this` 与等待恢复的 UAF 竞态（实测崩溃复现）。修复后任意并发下稳定。

**权衡**：bthread 挂起/唤醒在 4 核 VM 上调度开销大于 std::cv 阻塞 worker 的收益，吞吐 7813 → 2912，但换取了稳定性（配置中心写并发远低于此，可接受）。

### 发现 2：braft 日志 fsync 是写路径最大热点（13 倍差距）

对照实验：`--raft_sync=false`（关闭每次写日志 fsync）后 QPS 瞬时 **37614** vs 默认 2912，**13 倍差距**。fsync 是 Raft 持久性保证（崩溃恢复需要），是写路径固有成本。

**面试答法**：这是分布式系统的经典"性能 vs 持久性"权衡（etcd 同样面对）。默认 `FLAGS_raft_sync=true` 保证崩溃后不丢已提交日志；关闭可提升吞吐但风险是节点崩溃时可能丢已提交日志。正确做法是批量/异步 fsync，而非直接关闭。

> ⚠️ 已知局限：`raft_sync=false` 高吞吐（>20k QPS）下节点崩溃，根因待查（fsync=true 时被 fsync 限流掩盖）。故该配置仅实验用，默认配置（fsync=true）稳定。

## 混沌测试：`scripts/chaos_test.sh`

| 场景 | 操作 | 验证 |
|---|---|---|
| kill Leader | `kill -9` leader | 自动重选主（实测恢复 ~3s），写读恢复 |
| kill Follower | `kill -9` follower | 多数派继续服务，写读不中断 |
| 网络分区 | `kill -STOP` 节点（心跳/请求全不可达）| 集群排除节点继续服务，CONT 恢复 |
| 重启 | kill 后重启（数据保留）| 自动追赶日志/快照，重新入组 |

一致性验证器（后台）：持续写递增序号 → 立即可从 leader 读回新值（线性一致）；Watch 长轮询校验事件 revision 严格递增（不丢不重）。最终校验线性一致违规 + Watch 乱序违规数为 0。

### 混沌测试发现并修复的 bug（面试亮点）

**Watch 落在追赶节点时重放旧事件**：重启的落后节点在 catchup 期间重新 apply 旧日志，向客户端广播 `revision <= from_revision` 的已消费事件（实测 `from=57` 收到 `rev=9`），破坏"不丢不重"。

**修复**（commit d5b0f9e）：`WatchHub::Watch` 先等本节点追平到 `from_revision` 再进入重放/长轮询；5s 未追平返回 INTERNAL 让客户端保留锚点重试，**绝不返回低于 from 的 current_revision**。
