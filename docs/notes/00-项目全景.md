## 0.1 这是什么项目、为什么要做

### 背景：微服务配置管理的痛点

微服务架构下，每个服务的配置（限流阈值、开关、DB 连接串、灰度比例…）如果散落在**本地文件/环境变量**里：

- **改配置要改文件 + 重启/重新分发**，慢且易错；
- 几十个服务没有**集中视图**，不知道谁配了什么；
- 没法**审计**：谁在什么时候把某个配置从 X 改成了 Y；
- 改错了想**回退**，没有历史版本。

行业成熟解法就是 **etcd / ZooKeeper / Consul / Apollo** 这类"配置中心 + 注册中心"。**etcd** 是其中事实标准（Raft 共识 + MVCC + Watch）。

### 本项目的定位

> Configraft = **etcd 在 C++ 技术栈下的一个精简子集实现**，专注"分布式配置中心"这一种形态：**集中管理、实时生效（Watch 推送）、可一键回滚（MVCC 多版本）**，并强调**强一致**（默认线性一致读）。

为什么选这个题做校招项目，因为它一张图能同时打中后端岗位最常考的四块硬骨头：

| 考什么 | 本项目哪个点体现 |
|---|---|
| **分布式共识 / Raft** | braft 3 节点强一致集群、线性一致读（Lease） |
| **分布式存储 / 一致性模型** | MVCC + 全局 revision、Compaction、CAS |
| **高并发服务端** | brpc/bthread 运行模型、双协议单端口、长轮询 Watch |
| **可靠性工程** | 混沌测试、压测、全项目代码审查（UAF 等 9 项修复） |

> **面试话术**：不要一上来讲细节。先用 30 秒说清"我实现了一个对标 etcd 的分布式配置中心，解决微服务配置'集中管理 + 实时生效 + 可回滚 + 强一致'四个问题"，再问一句"你想先听架构还是先听一致性？"——把节奏掌握在自己手里（详见 0.5 讲稿）。

## 0.2 系统架构总览

### 分层结构（单节点视角 × N 个副本）

Configraft 是**"分层 + 多副本"**架构：逻辑上每个节点是自底向上的四层，物理上三个这样的节点用 braft 组成集群。**关键心法：把"对外 RPC"和"复制日志"彻底分层**——对外的服务层只面向一个抽象的 `ConfigNode` 编程，节点之间的一致性交给 braft 这一层。

```text
                         ┌─────────────────────────────────────────────┐
                         │              客户端 / 浏览器 / SDK            │
                         │        gRPC(h2) · HTTP REST · Watch长轮询     │
                         └───────────────┬─────────────────────────────┘
                                         │  同一端口 8001
┌────────────────────────────────────────▼──────────────────────────────────────┐
│                           API 服务层  (server/)                                │
│   KVService   ConfigService   WatchService   AdminService   DashboardService   │
│    (Put/Get/…)  (Publish/…)    (长轮询)      (/healthz等)     (静态资源)        │
│        统一走  brpc 单端口；REST 由 Rest 方法按 method+path 分发；CORS 处理      │
└────────────────────────────────────────┬──────────────────────────────────────┘
                                         │  只依赖抽象接口 ConfigNode
┌────────────────────────────────────────▼──────────────────────────────────────┐
│                            复制状态机层 (raft/state_machine)                    │
│   on_apply: 把 RaftCmd 串行喂给 Store → 成功后产生 Watch 事件 → 回执等待者       │
│   SaveSnapshot / LoadSnapshot (与 Store 交互做快照导出/安装)                     │
└───────────────────────────────┬──────────────────────────┬─────────────────────┘
                                │ 节点 A(Leader)           │ 节点 B / C (Follower)
┌───────────────────────────────▼──────────────────────────▼─────────────────────┐
│                         Raft 层  (braft v1.1.2, src/raft)                       │
│    RaftNode:  Apply(提交日志) / 线性一致读(Lease校验+追平) / AddPeer/RemovePeer   │
│    多数派提交 → on_apply 串行 → WatchHub 广播                                   │
└───────────────────────────────┬──────────────────────────┬─────────────────────┘
                                │ 本机直调                     │ Raft 内部复制(同端口)
┌───────────────────────────────▼──────────────────────────▼─────────────────────┐
│                         存储层 (store/ + common/storekey)                       │
│    LevelDB (MVCC 布局): k/{key} 主索引 · v/{rev}/{key} 历史 · cfg/{key}/{ver}    │
│    · meta/revision 全局时钟 · meta/compact_rev 回收水位 · WatchHub 广播事件      │
└──────────────────────────────────────────────────────────────────────────────────┘
```

### 关键组件表（先混个脸熟，后面逐章拆）

| 组件 | 代码位置 | 一句话职责 | 对应章节 |
|---|---|---|---|
| `ConfigNode`（抽象） | `src/raft/node.h` | 服务层唯一依赖的接口：写/读/Watch/元信息 15 个方法 | 03 |
| `RaftNode` | `src/raft/raft_node.cpp` | 集群实现：提交复制日志、Lease 线性一致读、成员变更 | 04/05 |
| `LocalNode` | `src/raft/local_node.cpp` | 单机实现：直接同步调 Store（调试/测试用），内部加锁 | 05 |
| `ConfigraftStateMachine` | `src/raft/state_machine.cpp` | `on_apply` 串行落库 + 广播事件 + 快照 | 04/05 |
| `Store` | `src/store/store.cpp` | LevelDB 封装：MVCC 读写、CAS、Compaction、快照导出/加载 | 04/05 |
| `WatchHub` | `src/watch/watch_hub.cpp` | Watch 长轮询分发：注册/重放/背压/续传 | 05 |
| 四个 Service + Dashboard | `src/server/*` | 对外协议；`server.cpp` 负责组装与 restful 映射 | 03 |
| `server_main.cpp` | `src/main/` | 启动：解析参数、强制开启 lease 等 FLAGS | 03 |

### 数据流（三句话版本，先背下来）

- **写**：客户端 → Leader API → `node->Apply(task)` → braft 复制到多数派 → commit → `on_apply` **串行**写入 LevelDB（推高 revision、产生 Watch 事件）→ 唤醒写等待者 → 返回客户端。
- **读（线性一致）**：客户端 → Leader API → 校验 **Leader Lease 有效** → 等 **applied ≥ commit** → 从本地状态机读 → 返回。（不经过 Raft 复制，所以读能到几十万 QPS。）
- **Watch**：客户端带 `from_revision` 发长轮询 → 挂到 WatchHub → 有变更事件立即返回（带新 revision 作续传锚点）→ 客户端用新 revision 再次请求；历史从 MVCC 重放。

## 0.3 全链路时序图（面试高频 · 一定要会自己画）

> 这是整套笔记**唯一一张"跨节点完整时序"**。面试官让你画架构/讲流程时，本质就是让你把下面几张图"画对"。**考核点是 term / index / revision 三个数字谁在推进、谁在等待谁**。

### (a) 一次写：Put → 落库 → 推送

```text
Client          Leader(node1)                Follower(node2/3)
  │  POST /v1/kv/k            │                       │
  ├──────────────────────────►│                       │
  │   KVService::Put          │                       │
  │                           │ 组 RaftCmd{key,val}    │
  │                           │ task.expected_term=T   │
  │                           │ braft::Node::apply     │
  │                           ├──── AppendEntries ────►│  日志写入(持久化/可关)
  │                           ├───────────────────────►│  (term=T, index=N)
  │                           │◄──── ack(多数派=含自己) │
  │                           │  标记 entry[N] 已提交    │
  │                           │  commit_index=N         │
  │                           │ on_apply(RaftCmd)       │
  │                           │   ApplyCmdToStore:      │
  │                           │    LevelDB.WriteBatch   │
  │                           │     (k/ + v/{rev}/ +    │
  │                           │      meta/revision=rev+1│
  │                           │      +cfg/...)  原子提交 │
  │                           │   closure->Finish(ok)   │
  │                           │   WatchHub.Broadcast    │──► 推送挂在 hub 的 waiter
  │◄──────── 响应(kv,version,rev)│                       │
```

**读图要点**：
1. 只有 **Leader** 能提交日志（写请求打到 Follower 会被回 NOT_LEADER + leader 地址）。
2. 多数派 = 3 节点时 2 个；"确认"指对方**持久化（可关 fsync）**了这条日志。
3. `on_apply` 只在 **Leader 本机**执行 → 状态机与日志逐条一致，天然解决"副本之间并发乱序"。
4. revision 递增、数据写入、Watch 事件三者是**同一个串行 apply 步骤**里完成的 → 顺序天然一致。

### (b) 一次线性一致读：Get

```text
Client          Leader(node1)
  │ GET /v1/kv/k          │
  ├───────────────────────►│ KVService::Get(serializable=false)
  │                        │ RaftNode::Get:
  │                        │  ① WaitLeaderLease()
  │                        │     循环 get_leader_lease_status()
  │                        │     LEASE_VALID? → 过 (NOT_READY 则 bthread_usleep(5ms))
  │                        │     含义: 本任期内 no-op 已提交 + 最近与多数派确认过
  │                        │  ② WaitAppliedCatchUp()
  │                        │     等 known_applied_index >= committed_index
  │                        │  ③ store_->Get(key)   ← 纯本地读, 不复制
  │◄─────── 响应(value,rev) │
```

**读图要点**：读不经过 Raft 复制（所以快）；正确性全靠 ①② 两道闸门把"过期读"挡在外面。为什么这两步就够，是第 01/04 章的重头戏。

### (c) 一次 Watch 长轮询（含断线重连）

```text
Client(node1端口)                    集群任意节点(以Leader为例)
  │ GET /v1/watch?from_revision=5        │
  ├──────────────────────────────────────►│  WatchHub::Watch
  │                                       │  ① 若本地落后 from_revision → 等追平(≤5s)
  │                                       │  ② Register(waiter) 挂入 hub
  │                                       │  ③ 重放 (5, current] 区间历史事件(来自 v/)
  │                                       │  ④ 没新事件 → 挂起等待(bthread cv,≤timeout)
  │        (另一客户端 Publish key=v)        │
  │                                       │   on_apply → Broadcast → 命中 waiter
  │◄──────── 200 响应 events[rev=6],current_revision=6
  │  立刻用 from_revision=6 再次请求 ◄──────┘  (断点续传, 不丢不重)
```

### (d) 故障转移：kill Leader

```text
        node1(Leader) 挂了                node2/3
              │                             │ 选举超时到期(随机化)
              │                             │ node2 发起选举 term+1
              │                             │ 获得多数派投票 → node2 成为新 Leader
              │                             │ 提交本任期第一条 no-op 配置日志(关键!)
              │                             │   → 旧任期已提交日志被其日志覆盖/补齐
              │                             │ 开始接收写请求(客户端之前已按重定向更新地址)
```

**读图要点**：故障转移后能安全接管写的关键是——**新 Leader 必须先提交一条 no-op 配置日志**。这既是 Raft 提交新日志的前提，也是线性一致读 Lease 论证的前提（详见 01/04）。

## 0.5 30 分钟面试讲稿（分层框架）

> 原则：**讲稿不是背稿**，是给你 4 个"可伸缩的模块"。面试官时间多就往深讲，时间少就每层只讲第一句。每个模块末尾都主动抛一个"引导钩子"，把面试官往你会的地方引。

### 开场（≤30s）：一句话定位 + 抛结构

> "我做的项目是一个**对标 etcd 的分布式配置中心**，解决微服务配置'集中管理、实时生效、可一键回滚'的问题。整个系统可以分成三层理解：**对外是 gRPC+HTTP 的 API，中间是 braft 强一致复制，底下是带 MVCC 的 LevelDB 存储**。我重点讲两个最硬的部分——**一致性怎么保证**，和 **Watch 怎么做到有序不丢**，你看可以吗？"

（钩子：主动框定范围，避免被带到冷门角落。）

### 模块 1 · 架构与功能（3~5 min）

- 讲 0.2 的**分层图**：为什么 API 层只依赖抽象 `ConfigNode`（换 LocalNode/RaftNode 服务层零改动）。
- 快速过功能清单：KV / 配置多版本发布回滚 / CAS / Watch / 成员变更 / Dashboard。
- （钩子）"我实现的都是**对外可见的功能**，但真正的难点是它们背后的一致性——所以下面重点讲读写的正确性。"

### 模块 2 · 强一致与线性一致读（10 min，全场最硬）

1. **写的一致性**：所有写 = 一条 RaftCmd 进复制日志，多数派确认后 `on_apply` **串行**落库 → 天然线性一致，且天然串行让 MVCC revision 有序。
2. **读的一致性为什么难**：见 01/04。核心逻辑链要能讲（建议配画图）：
   - "Leader 直接读本地为什么不够？" → 本地状态机可能没追上已提交日志；
   - "所以要么走 ReadIndex，要么走 Lease" → braft v1.1.2 **没有** ReadIndex API（源码确认过）；
   - "我用 Lease：Lease VALID ⟺ 本任期 no-op 已提交且最近与多数派确认 → 旧任期已提交写都已进状态机 → 再等 applied≥commit → 本地读"。
3. （钩子）"这一步的正确性我**不是拍脑袋**的，后面有 kill Leader/网络分区的混沌验证，你要感兴趣我可以讲验证方法。"

### 模块 3 · Watch 长轮询（5 min）

1. 为什么 HTTP 长轮询不是 gRPC 流（可演示性 / 实现简单；诚实说清取舍）。
2. revision 断点续传：锚点 = "最后一条事件的 revision"（不是 store 当前值，为什么——防漏事件）。
3. 慢消费者背压：每订阅者缓冲 1024，满了断开 + 返回锚点重连重放，**绝不让慢消费者阻塞 on_apply**。
4. （钩子）"Watch 的历史事件是从 MVCC 的 v/ 记录重放的，这正好是存储设计里 revision 布局的用处，要不要看下我 LevelDB 的 key 怎么设计的？"

### 模块 4 · 可靠性：踩坑 + 数字（5~10 min）

- 挑 1~2 个最"亲写"的坑讲透（06 章素材），建议主推 **std::cv 假死** 或 **快照并发 UAF**——这两个最能证明代码是你写的。
- 报数字前先报环境（8 核 / 环回 / 加固后），再报表（07 章）。
- 主动承认局限（无鉴权、fsync 可关），并说生产化第一件事做什么。

### 收尾（30s）

> "这个项目我做完了从协议到存储到混沌验证的完整闭环。刚才我重点讲了一致性和 Watch；如果你对 **MVCC 存储布局 / 性能优化 / 代码审查修复**哪块感兴趣，我可以展开。"
