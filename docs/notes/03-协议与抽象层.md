# 03 · 协议与抽象层：系统怎么组织起来的

> 本文件拆解"架构层"的三个抽象：**proto 协议**、**ConfigNode 接口**、**Server 组装（单端口双协议）**。这是面试官问"你这个系统整体是怎么搭出来的"时你要讲的层次。代码集中在 `proto/configraft.proto`、`src/raft/node.h`、`src/server/server.cpp`。

---

## 3.1 proto 协议设计（`proto/configraft.proto`）

### 3.1.1 一条铁律：对外 API 与内部日志指令分离

proto 里明显分成两类 message：

- **对外 API**（`PutRequest`/`KVResponse`/`PublishRequest`…）：是"客户看的"，语义是 RPC。
- **内部 `RaftCmd`**（`oneof cmd`：put/delete/cas/publish/rollback/batch_put）：是"写进 Raft 复制日志、由状态机 `on_apply` 消费"的**指令**。

为什么必须分开：
1. **协议不耦合日志格式**——对外 API 变了，不必重放旧日志（旧日志仍是当时的 RaftCmd）。
2. 一条对外写请求可能映射成一条 RaftCmd；未来加功能（如事务）只加 RaftCmd 类型。
3. 快照、恢复、多副本只认 RaftCmd 这个"确定性输入"，保证 SMR 各副本执行一致。

### 3.1.2 错误码设计（`configraft.proto:16-25`）

```text
0  OK           1 KEY_NOT_FOUND   2 CAS_FAILED     3 NOT_LEADER
4  VERSION_NOT_FOUND  5 COMPACTED  6 INVALID_ARGUMENT  100 INTERNAL
```

设计要点（背住能解释为什么这么定）：
- `NOT_LEADER` 的响应里**必须带 leader 地址** → 客户端靠它重定向（README 与代码都这么约定）。
- `COMPACTED` 语义 = "你要求的 revision 之前的历史已被回收" → 响应带 `current_revision` 让客户端从新锚点续传。
- `VERSION_NOT_FOUND` 与 `COMPACTED` 分开：前者是"单 key 的某个 version 不存在"，后者是"全局 revision 段被回收"，语义别混。
- 写路径空 key 拒在入口：`INVALID_ARGUMENT(6)`，早失败避免污染命名空间。

### 3.1.3 `option cc_generic_services = true` 与空请求 message

- brpc 依赖 protobuf 的 **generic service** 机制生成 C++ service 基类 → 必须 `option cc_generic_services = true;`（包名 `configraft.v1`，C++ 侧在 namespace configraft 内 `using namespace v1`）。
- RESTful 入口统一走一个**空请求**的方法，如 `rpc Rest(KVHttpRequest) returns (KVResponse)`：因为 HTTP 请求的字段全部来自 **URL 路径 + body**（body 经 `json2pb` 解析进各 request），Rest 方法的 protobuf 请求本身就是空的（详见 3.3 的路由设计）。

### 3.1.4 `SnapshotData`：快照的传输格式

`message SnapshotData { int64 revision; repeated KV kvs; repeated KV cfg_kvs; }`（`configraft.proto:161-167`）。
- 不只主索引 `kvs`，还带 **`cfg_kvs`**（配置多版本索引 `cfg/` 前缀）——否则新节点装快照后**按版本读配置（GetConfig(version>0)）与历史会丢**（这是审查发现并修复的 M2 项，见 06 章）。
- 带全局 `revision`，让新节点知道自己追到哪个时间点。

## 3.2 ConfigNode 抽象：服务层只对着接口编程

### 3.2.1 为什么需要这一层

如果没有抽象层，服务层就要区分"我现在是单机还是集群"，代码到处 `if`。加一个 `ConfigNode` 接口，让**服务层只依赖接口、永远不知道底下是谁**。

### 3.2.2 接口清单与双实现

`ConfigNode`（`src/raft/node.h`，约 15 个纯虚方法）分类：

| 类别 | 方法（示意） | 单机 LocalNode | 集群 RaftNode |
|---|---|---|---|
| 写 | `Apply(cmd)` | 加锁 → 直接 `ApplyCmdToStore` + 广播 | 提交 braft 日志，等 apply 结果 |
| 读 | `Get(key, serializable)` | 直接本地读 | Lease 校验 + 追平后本地读 |
| 配置 | `GetConfig` / Watch 相关 | 本地 | 本地（经 lease） |
| 运维 | `Compaction / AddPeer / RemovePeer` | 仅 Compaction 有效 | 转发 braft |
| 元信息 | `IsLeader / LeaderId / Term / CommitIndex / AppliedIndex / Peers / CurrentRevision` | 单机恒 Leader | 取 braft NodeStatus |

`server.cpp` 里组装：`Init` 时看启动参数——`--node`/`--peers` 非空则建 `RaftNode`，否则建 `LocalNode`（`src/server/server.cpp`）；服务层构造时拿 `node_.get()` 注入（KV/Config/Watch/Admin 都只持 `ConfigNode*`）。

### 3.2.3 好处（面试讲三点）

1. **测试友好**：单元测试可用一个"内存 Node"替身，不必起 Raft（`raft_cas_test` 恰恰反过来，为了测真 Raft 起了单节点 braft 组，见 07 章）。
2. **渐进开发**：M1 先做单机 LocalNode 把功能跑通，M2 再引入 RaftNode，**服务层一行没改**——这就是里程碑能平滑推进的架构原因。
3. **语义收敛**：所有"状态修改"只经 `ConfigNode::Apply` 一个口子 → 多副本一致性由实现各自保证，服务层无脑调用即可。

> 面试一句话："我把'节点'抽象成 ConfigNode 接口，服务层永远不知道底下是单机还是 Raft 集群。这让单机调试和集群部署共用同一套服务代码，也让 M1→M2 从本地到 Raft 的切换对业务零改动。"

## 3.3 Server 组装：brpc 单端口承载 gRPC + HTTP + Raft

### 3.3.1 一个端口怎么同时跑三种流量

brpc 的 **Server** 可以在**同一个端口**上：
- 注册业务 pb service → 得到 **gRPC 路径**（如 `/configraft.v1.KVService/Put`，走 HTTP/2，客户端协议名 `"h2"`）；
- 通过 **restful 映射**把 URL 路径挂到 service 方法 → 得到 **HTTP REST**；
- `braft::add_service(server, port)` 把 Raft 的 RPC service 也挂到**同一 brpc Server** → Raft 内部通信（AppendEntries/Vote/Snapshot）与业务共用端口。

这就是 README 说的"同一端口提供 gRPC + HTTP 双协议接口与 Raft 内部通信"。对内网部署（所有节点端口一致）和 Docker 端口映射都极方便。

### 3.3.2 restful 映射：一个关键坑和它的解法（重点，能讲清 = 真懂 brpc）

**现象/坑**：brpc 的 restful 映射**不支持 HTTP 方法前缀**（不能写 `GET /v1/kv/k => Get`），而且——**一旦把"具体方法名"映射到 URL，该方法就失去普通 gRPC 路径**。

本项目的映射（`server.cpp` 的映射常量）：

```text
KVService     "/v1/kv/* => Rest"            (Rest = 专用空请求方法)
ConfigService "/v1/config/* => Rest"
WatchService  "/v1/watch/* => Rest"
Dashboard     "/dashboard => Rest, /dashboard/* => Rest"
AdminService  "/healthz=>GetHealth, /addpeer=>AddPeer, /removepeer=>RemovePeer"  ← 直接映具体方法!
```

**解法**：KV/Config/Watch 映射到统一空方法 `Rest`，在 `Rest` 内部按 **`method + unresolved_path`** 手动分发：
- KV：`GET → Get`、`DELETE → Delete`、`POST /cas → CAS`、`POST /batch → BatchPut`、其余 `POST /{key}` → Put（`src/server/kv_service_impl.cpp`）；
- Config 同理分发 Publish/GetConfig/Rollback；
- body 用 `json2pb::JsonToProtoMessage` 解析进对应 request message。

**为什么不能图省事直接 `/v1/kv/put => Put`？** 因为那样 `KVService::Put` 的 gRPC 路径就没了。这个坑在 **AdminService 上真实发生**（`GetHealth/AddPeer/RemovePeer` 被直接映射后，它们走 gRPC 全部返回 Unimplemented/404）。因为 Admin 是**纯运维面、面向 curl/浏览器**，所以干脆**设计成只走 HTTP**（README 里写明了）。

> 面试一句话："brpc 的 restful 映射有两个特性：不支持按 HTTP 方法分发，且具体方法一旦被映射就占用掉它的 gRPC 路径。所以 KV/Config/Watch 这类需要 gRPC 的服务，我把 REST 入口收敛到一个专用 Rest 方法里按 method+path 手工分发；Admin 纯运维、只需 HTTP，才直接映射具体方法。这是我在真机验证（gRPC 404）后得出的根因与方案。"

### 3.3.3 `/healthz` 为什么不是 `/health`（又一个 brpc 细节坑）

brpc 内置 **HealthService 的短名是 `health`**，restful 映射按"路径首段 = service 短名"注册 → 用 `/health` 会与内置 HealthService **冲突导致 Server 启动失败**。所以健康检查路径定为 **`/healthz`**（`server.cpp` 注释说明）。

### 3.3.4 CORS（跨源资源策略）与安全收紧

**为什么需要 CORS**：Dashboard 页面在 `http://127.0.0.1:800X/dashboard` 打开，页面 JS 却要 fetch 另一端口 `800Y`（Leader）→ 浏览器视为**跨源**，需要服务端回 `Access-Control-Allow-Origin` 等头 + 处理预检 OPTIONS。

- `rest_util.h` 的 `IsAllowedOrigin`：**仅当请求 Origin 的主机与 Host 相同（去掉 scheme/port 比对）才回显 Origin**。
- `HandleCorsPreflight`：放行则回显 `Access-Control-Allow-Origin` + `Vary: Origin`，恒设 Allow-Methods/Headers；OPTIONS 直接回 200。
- **为什么不能 `*`**：本项目**无鉴权**，若 `*` 通配，任意恶意网页都能跨站读写配置/成员/数据（H3 高危项，06 章）。

> 另有个 C++ API 细节：brpc 的 `cntl->http_request().GetHeader(name)` 返回 `const std::string*`，**可能为 nullptr**，必须先判空再解引用（`rest_util.h`）。这是很典型的"框架返回裸指针"的坑。

### 3.3.5 关闭内置服务面板（安全加固）

`brpc_opts.has_builtin_services = false`：brpc 默认在共享端口开 `/status` `/vars` `/flags` `/connections` `/rpcz` 等内置页，会**泄露运行参数与内部指标**——面向内网/Dashboard 的共享端口应关闭（M7 审查修复项）。

### 3.3.6 Dashboard 静态资源托管

- DashboardService 用 `/dashboard/* => Rest` 托管 `web/` 目录静态文件（GET-only，按扩展名设 Content-Type，防 `..`/绝对路径穿越）。
- **根路径 `/` 不能用作入口**：`/` 被 brpc 内置 IndexService 占用、无法用 restful 映射替代 → 入口必须是 `/dashboard`。这也是前端**必须用绝对路径 `/dashboard/style.css`** 引资源的原因（相对路径在无尾斜杠的 URL 下会 404）。

### 3.3.7 其它启动细节（Server 组装清单）

- **WatchHub 单实例**：`ConfigraftServer` 持 `unique_ptr<WatchHub>`，声明在 node_ 之前使析构逆序先销毁（避免反向访问），同一指针注入 LocalNode/RaftNode。
- **Compaction 后台线程**：`server.cpp` 起一个循环线程（每 60s 一次，每 key 保留 10 版），用 `condition_variable::wait_for` 睡眠 + 析构时 notify 立即 join（优雅关停，HTTP 集成测试多起停必需）。
- **bthread worker 数**：`num_threads = 4`。
- **入口 `server_main.cpp`**：解析 gflags 后**强制** `braft::FLAGS_raft_enable_leader_lease = true`（放 Parse 之后，防止命令行 `--raft_enable_leader_lease=false` 覆盖成不安全模式），然后启动 Server。
