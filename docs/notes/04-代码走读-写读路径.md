## 4.1 写路径全流程走读

### 4.1.1 入口：两种协议汇到同一个 `DoPut`

gRPC 入口 `KVService::Put`（`kv_service_impl.cpp`）与 HTTP 入口（`Rest` 分发后调 `DoPut`）最终都汇聚到同一个内部函数 `DoPut`：

```cpp
// 伪代码: DoPut(key, value)
1. 校验: key 非空? 否则回 INVALID_ARGUMENT          // 空 key 在入口拒绝
2. 组装内部指令 RaftCmd{ put{key,value} }           // 见 03.1: 对外请求→内部指令
3. node_->Apply(cmd)                                // 只调用抽象接口, 不关心单机/集群
4. 若返回 NOT_LEADER: 把 LeaderId 写进响应的 message, 回给客户端重定向
```

### 4.1.2 `RaftNode::Apply`：把指令变成一条复制日志（`src/raft/raft_node.cpp`）

```
1. IsLeader()? 否 → 回 NOT_LEADER + LeaderId()        // 只有 Leader 能定序
2. 序列化 RaftCmd → 日志数据
3. 组装 braft::Task task{ data, 回调 closure, expected_term }
   task.expected_term = fsm_->leader_term()            // 防 ABA(见下)
4. node_->apply(task)                                  // 异步: 交给 braft 复制
5. ApplyClosure::WaitFor(...)                          // 同步等 on_apply 结果
6. 返回结果的 code/kv
```

**`expected_term` 防 ABA（必讲）**：`apply` 是异步的——从"把日志交给 braft"到"复制完成、被 on_apply"之间，**本节点可能已经不再是那个任期的 Leader**（比如刚被赶下台又立刻重新当选）。若 `task.expected_term != 当前任期`，braft 会**拒绝**这条日志并让回调立即以失败返回。这防止了一种隐蔽错误：**旧任期 Leader 的日志被当成新任期写入**，绕过节流/安全保证。相当于给"我提交时是 Leader"补了一个"提交完成时我仍是该任期 Leader"的校验。

### 4.1.3 braft 复制与 `on_apply`（`src/raft/state_machine.cpp`）

braft 把日志复制到**多数派**后，调用状态机回调 `ConfigraftStateMachine::on_apply`（每节点一份，Leader 先于 Follower 执行到）：

```cpp
// on_apply(iterator) 伪代码
1. AsyncClosureGuard guard;                    // 延后执行日志携带的 closure(见 4.2)
2. for 每条已提交日志:
      ParseFromZeroCopyStream 解出 RaftCmd     // 与对外请求 message 解耦
      ApplyCmdToStore(cmd, &out)               // 见下: 真正写 LevelDB
3. 对 Leader: 当 iter.done() 非空 → closure->Finish(result)   // 唤醒等结果的那一侧
   写失败时 → 上报 EIO
4. 无论 Leader/Follower: WatchHub::Broadcast(out.events)      // 广播 Watch 事件
```

**`ApplyCmdToStore`**（`src/store/store_ops.cpp`）按 `RaftCmd` 的 `oneof` 分派到 Store 的对应写方法（Put/Delete/CAS/Publish/Rollback/BatchPut），每个成功的方法返回该操作生成的 **Watch 事件**（`MakeEvent`，type=`PUT`/`DELETE`）。

### 4.1.4 Store 落盘：一个 WriteBatch 原子提交（预告 05 章详讲）

以 Put 为例，`Store::PutLocked` 做的事（`src/store/store.cpp`）：

```cpp
rev = NextRevisionLocked(&batch)              // 读 meta/revision, +1, 写回 batch
batch.Put(main_key(key),     新KV(含rev,ver)) // k/{key}: 主索引(最新值整体)
batch.Put(version_key(rev,key), 新KV)         // v/{rev:16hex}/{key}: 历史版本
Publish 语义时再 batch.Put(cfg_key(key,ver))  // cfg/{key}/{ver}
batch 原子提交                               // 全部成功或全部失败
```

**一次写 = 一个原子 WriteBatch**：数据与 revision 一起提交，任何一步失败都整体回滚 → 不可能出现"revision 推进了但数据没写进去"的节点发散。

### 4.1.5 写给谁返回？——`WaitFor` 与 `Finish` 的配对

- Leader 侧：客户端线程阻塞在 `ApplyClosure::WaitFor`（见 4.2）；
- on_apply 侧：日志条目携带的 closure 在 `iter.done()` 处被 `Finish(result)` 唤醒；
- **Follower 不唤醒任何人**（没有客户端在等它），它们只执行 `ApplyCmdToStore` + `Broadcast`——这就是"Watch 可以挂在 Follower"的基础。

### 4.1.6 一次写的完整顺序（背图）

```
Client → KVService.Put
  → RaftNode::Apply{ expected_term=cur_term }
  → braft 复制到多数派(fsync 可选)
  → commit_index 推进 → on_apply(本机串行)
      → ApplyCmdToStore → LevelDB.WriteBatch(数据+revision) 原子提交
      → closure->Finish → 客户端拿到响应
      → WatchHub.Broadcast → 推给所有长轮询订阅者
```

## 4.2 同步等待 apply 的并发原语（M7 修复的硬骨头）

### 4.2.1 问题：braft 可能在 `apply()` 返回前就释放 closure

写路径需要"等 on_apply 完成"，但 braft 的回调机制是：**braft 可能在 `node_->apply()` 还没返回时就已经复制完成并调用了 closure（`Run()` 里 `delete this`）**。于是"等结果"的代码如果直接访问 closure 内部成员，就是**访问已释放对象 → UAF**。实测：`fsync=false` 高吞吐压测时会 segfault in `bthread_mutex_lock`（`src/raft/state_machine.h` 注释记录）。

### 4.2.2 修复：把"等待状态"从 closure 里拆出来，用 shared_ptr 托底

`ApplyClosure` 结构（`state_machine.h`）：

```cpp
struct WaitState { bthread::Mutex mu; bthread::ConditionVariable cv; bool done; /*结果*/ };
// closure 持 shared_ptr<WaitState>
// 等待方: WaitFor() → { lock; while(!done) cv.wait(); }    // 持 shared_ptr, 不怕 closure 先死
// on_apply: Run()/Finish() → { 置 done=true; notify; delete this; }
```

关键：**等待方持有 `shared_ptr<WaitState>`，与 closure 生命周期解耦**——closure 被 `delete` 也不影响等待方安全读结果。这就是"用独立 WaitState 防 UAF"。

### 4.2.3 为什么不用 std::condition_variable（worker 假死）

- `WaitState` 里的锁/条件变量**必须是 bthread 原语**（`bthread::Mutex`/`bthread::ConditionVariable`）：
  - std 同步：bthread 阻塞时**占住底层 pthread worker** → `num_threads=4` 的 worker 被高并发写占满 → 节点假死（能 ping 通但不再处理请求）；
  - bthread 原语：只挂起当前 bthread，worker 被让出继续跑 on_apply/网络回调。

- **备选方案试错史**（M7，面试加分）：
  - `std::cv`：快（~7813 QPS）但假死 ❌；
  - `bthread::cv`：稳定，引入一点 bthread 调度开销 ✅（最终采用）；
  - `bthread_usleep` 轮询：慢（~2500 QPS）❌；
  - `bthread::butex`：能更快但**在 pthread 上下文挂死无法唤醒** + 高吞吐资源问题，弃用 ❌。

> 面试一句话："写请求要同步等 on_apply，但 braft 可能在 apply() 返回前就销毁 closure。我把等待状态拆成独立 WaitState（shared_ptr 持有）防 UAF；并且等待必须用 bthread 条件变量——用 std 条件变量会把 4 个 pthread worker 占死导致假死。这两点都是压测真实撞出来的。"

## 4.3 线性一致读：完整代码走读 + 正确性证明

### 4.3.1 `RaftNode::Get`（`src/raft/raft_node.cpp:166`）

```cpp
// Get(key, serializable) 伪代码
if (serializable) { return store_->Get(key); }   // Follower 本地读, 允许轻微过期

// ---- 强一致路径: 只允许在"证明自己是唯一且最新的 Leader"后本地读 ----
if (!IsLeader()) return NOT_LEADER + LeaderId();  // 读也要 Leader? 见 4.3.4

// ① 等 leader lease 有效 (最久 ~1000ms)
if (!WaitLeaderLease(1000ms)) return INTERNAL("leader not ready");  // ★不填自己地址

// ② 等 applied ≥ commit (最久 ~1000ms)
if (!WaitAppliedCatchUp(1000ms)) return INTERNAL("apply lag");

// ③ 本地读: 此刻状态机包含一切此前已提交的写
return store_->Get(key);
```

### 4.3.2 两步等待的实现细节

**`WaitLeaderLease`**（`raft_node.cpp`）：

```cpp
循环:
  status = node->get_leader_lease_status()   // braft 提供
  if LEASE_VALID   → 返回 true               // 见下: lease 有效 = 通过两道证明
  if EXPIRED/DISABLED → 返回 false           // lease 已过期, 不可信
  if NOT_READY    → bthread_usleep(5ms) 继续  // 刚当选/未就绪: 挂起 bthread 自旋,
                                              // 不占 pthread worker, 直到超时(1000ms)
```

**为什么 LEASE_VALID 就是"安全"的信号**（本项目的核心论证，见 4.3.3）——braft 的 leader lease 只有在 **Leader 提交了本任期的配置条目（等价 Raft no-op）且最近与多数派成功交互** 后才 VALID。LEASE_VALID 一步同时给出"no-op 已提交"与"我是唯一 Leader"两个保证。

**`WaitAppliedCatchUp`**（`raft_node.cpp`）：

```cpp
循环:
  status = node->get_status()                 // 单次采样, 同时拿两个指标
  if known_applied_index >= committed_index → 返回 true
  bthread_usleep(100us)
```

- **为什么还要②**：lease 只保证"没有更新的 Leader 提交过新写、且旧任期已提交写在我的日志里"，但**不保证我已经把它们 apply 进状态机**（可能刚当选、刚恢复、还在追赶）。② 把"在日志里"变成"在状态机里"。
- **为什么用"单次采样 applied≥commit"**：避免跨快照安装瞬间的误判（装快照时 applied 可能短暂跳到快照对应位置又跳回）。

### 4.3.3 正确性证明链（面试最硬的一块，要能一步步讲）

> 目标：证明"第③步的本地读结果，等于某个把此前所有已提交写都生效后的线性化点上的状态"。

**引理 A（no-op 已提交 ⇒ 旧任期已提交写都在本 Leader 日志里）**
新 Leader 当选后，braft **自动追加并提交一条配置条目（no-op）**。它提交成功意味着被多数派接受；由 **Leader Completeness**（01 章 1.3.3）：此前任何任期已提交的日志条目，必然出现在之后所有 Leader 的日志中 ⇒ 本 Leader 日志包含它们。

**引理 B（LEASE_VALID ⇒ 本任期 no-op 已提交 且 我是唯一 Leader）**
Lease 靠多数派周期性确认续租；VALID 时：①本任期配置条目已提交（否则 lease 不会进入 VALID）；②最近与多数派有过交互 ⇒ 多数派在 lease 内**不会**投给任期更高的候选者（开启 lease 后 Follower 遵守 lease 不参与更高任期选举）⇒ 不存在我不知道的新 Leader ⇒ 不会在我读的窗口里冒出一个提交过新写的更高任期 Leader。

**引理 C（applied ≥ commit ⇒ 日志里的已提交写已进状态机）**
② 保证本节点状态机已经应用到 commit_index ⇒ 引理 A 那些"旧任期已提交写"都已生效。

**结论**：第③步本地读发生前，状态机 ≥ 一切"在 lease 确立时刻之前已提交"的写；且 lease 有效期内没有别的 Leader 能提交我未见的写 ⇒ 读到的是线性一致的最新状态。若 lease 失效/追不上，读**拒绝服务**（返回 INTERNAL）而非返回过期值——**牺牲可用性，保住正确性**。

### 4.3.4 三个工程细节（防被问倒）

1. **为什么读也要重定向到 Leader**：强一致读路径里，Follower 没有 lease 也不保证自己的状态机追上 commit——只有 Leader 能做"唯一 Leader"证明。要 Follower 承担读，只能用 `serializable=true`（放弃线性一致）。
2. **"不是 Leader 但 lease 没就绪"时返回什么**：返回 `INTERNAL("leader not ready")`，**绝不把 `LeaderId()` 填给自己**（`raft_node.cpp` 注释）。否则客户端拿到"Leader 是你"会**循环打回本节点**死锁。这是 README/代码里特意注释过的自我重定向陷阱。
3. **读为什么不阻塞写**：读是本地 Store 读（共享锁）；写发生在 braft 复制层。两者在 Store 层以读写锁共存（05 章 4.3 讲 Store 线程模型）。

### 4.3.5 一次线性一致读的代码时序（再背一遍）

```
KVService::Get → RaftNode::Get
  → IsLeader?                                    // 否: NOT_LEADER+leader, 客户端重发
  → WaitLeaderLease(≤1s): get_leader_lease_status
      LEASE_VALID?   (否 → NOT_READY 自旋 5ms / EXPIRED 失败)
  → WaitAppliedCatchUp(≤1s): get_status, applied≥commit? (否 → 100us 自旋)
  → store_->Get(key) → 返回(值, version, revision)
```

## 4.4 写路径的扩展语义：CAS 为何"原子"（预告）

`CompareAndSwap` 之所以能在**无锁**下原子，是因为它**本身就是一条 RaftCmd**：

```text
CAS{key, expect, value}
 → 作为一条 RaftCmd 进日志 → on_apply 串行执行:
    读当前(key) → 与 expect 比对:
      匹配   → 写新值(NextRevision) → 产生 PUT 事件 → 返回成功
      不匹配 → 返回 CAS_FAILED        ← 注意: 不消耗 revision!
   → 并发 N 个 CAS: 日志序就是执行序, 恰一个成功, 天然原子
```

- **原子性来源 = Raft 串行 apply**（单 Leader 下不存在并发比较），不是靠锁。
- **失败不消耗 revision**：revision 只在"真写入"时推进，CAS 失败不产生任何数据变化 → 语义干净（05 章 5.2 详述，含 `expect=""` 的 tombstone 语义）。
