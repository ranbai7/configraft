## 5.2 性能三坑（M7，每个都能讲成一个小故事）

### 坑一：`std::condition_variable` 阻塞 bthread → worker 假死

**现象**：高并发写压测，节点"能 ping 通但不再响应任何请求"（假死），像死锁但不是死锁。
**定位**：brpc 是 **M:N 模型**，bthread 阻塞在 `std::cv` 上时**占住底层 pthread worker**；`num_threads=4` → 4 个阻塞请求就把 worker 全占 → on_apply / 网络回调都没 worker 可跑。
**修复**：等待原语换成 **`bthread::Mutex` + `bthread::ConditionVariable`**（挂起的是 bthread，worker 被让出）。
**试错记录**（讲了显深度）：`std::cv`（快但假死）→ `bthread_usleep` 轮询（2500 QPS 太慢）→ `bthread::butex`（崩溃：pthread 上下文挂死无法唤醒）→ **`bthread cv`（稳定）最终采用**。

### 坑二：Apply closure 提前释放 → UAF（gdb 定位）

**现象**：`fsync=false` 高吞吐下 segfault in `bthread_mutex_lock`。
**定位**：`node_->apply()` **返回前** braft 就可能复制完成并调用 closure（`Run()` 里 `delete this`）→ 等待方访问已释放成员的 **UAF**。
**修复**：把"等待状态"拆到独立 `WaitState`（`bthread::Mutex+cv+done`），closure 与等待方都持 **shared_ptr** → 等待方与 closure 生命周期解耦。详见 04 章 4.2。
**调试经验**：`gdb -batch` 起节点可能不复现（改变时序）——这类竞态要**高吞吐压测复现**，不是单步调试。

### 坑三：fsync 是写路径最大热点

**现象/结论**：同环境 `--raft_sync=false` 比默认快约 **8–10 倍**（3 节点写 ×64：10.0k → 28.2k QPS）。
**解释**：Raft"多数派持久化"里的"持久化"= fsync 落盘；这是"崩溃不丢已提交日志"的**固有代价**，不是代码问题。压测关 fsync 只为看吞吐上限，**生产必须开**。

## 5.3 全项目代码审查：9 项修复（2026-08，commit e5d737b）

> 背景：4 个子代理并行审查 Raft 核心/服务层/存储/前端，发现约 38 项，选"正确性+安全核心"范围修 9 项。**面试讲这 9 项比讲功能更能证明工程成熟度**。每项按"问题→根因→修复→验证"背。

| 编号 | 问题（严重度） | 根因 | 修复 | 验证 |
|---|---|---|---|---|
| **H1** | LoadSnapshot 与并发读/Compaction 无同步 **UAF**（HIGH） | `db_.reset()` 重建 DB 时无锁，旧 `db_` 正被并发用 | Store 引入 `shared_mutex`：重建持独占锁，读/写/Compaction/快照导出持共享锁；拆 `*Locked` 防锁重入 | 黑盒：装快照+并发读不再崩；coredump 回归 |
| **H2** | 单机 LocalNode 并发写 → **revision 重复**（HIGH） | 无 Raft 时多 worker 并发调 Apply，revision 读-改-写竞态 | `LocalNode::Apply` 加 `std::mutex` 串行 | 单机并发写 1024 条 revision 严格递增 |
| **H3** | 通配 CORS `*` → 任意网页可跨站读写（HIGH） | 服务无鉴权 + ACAO `*` | 收紧为仅同主机（去端口比 Host）回显 Origin | 恶意站点请求无 ACAO 头，同主机放行 |
| **M1** | 快照 revision 在 LevelDB snapshot 外读取 → 跨节点编号发散 | 导出 revision 与数据不原子 | `Store::ExportSnapshot` 同一 snapshot 内读 revision+k/+cfg/ | 新节点 revision 与源一致 |
| **M2** | 快照不含 cfg/ 索引 → 新节点按版本读配置丢失 | `SnapshotData` 只带主索引 | proto 加 `cfg_kvs=3` 随快照导出/恢复 | add_peer 后 GetConfig(v1..v5) 全可用 |
| **M3** | GetHistory 层级 key 前缀碰撞跨 key 泄漏 | key="a" 与 "a/b" 的 cfg/ 前缀重叠 | 遍历时校验 `kv.key()==key` | 单测回归 |
| **M4** | meta/revision 独立写 + batch 失败 → 状态发散 | revision 与数据非原子 | `NextRevisionLocked(WriteBatch*)` 并入同批；on_apply 上报 done 状态 | 失败注入测试 |
| **M5** | 空 key 污染命名空间 | 缺参数校验 | proto 加 `INVALID_ARGUMENT=6`，KV/Config 写路径拒绝空 key | http_test 空 key 返回 code=6 |
| **M7** | brpc 内置服务面板（/status /vars）泄露 | 默认开启 | `has_builtin_services=false` | `/status` 404 |

> **面试怎么讲**："我做完功能后做了一次全项目代码审查，四维并行、按严重度分级，选了正确性+安全相关的 9 项修复。最硬的是 H1——快照安装时会 reset 数据库指针，跟并发读冲突就是悬垂指针；我用一把 shared_mutex 把'重建'和'访问'隔开，还因为 shared_mutex 不可重入把 Store 拆成了公共方法+*Locked 两层。修完在同环境复测，性能零回退（±5% 内）。"（数字见 07 章）

### 审查发现但**有意未修**的记录（被问"有没有留坑"时用）

- **无鉴权 + addpeer**：任何人可调用成员变更（数据外泄面）→ 需 token/IP 白名单，**未纳入本次范围**，README 安全模型已声明"面向受信内网"。若生产化，第一件事是鉴权。
- **apply 非幂等**（U2）：崩溃后重放日志可能 revision 漂移 → 需把 applied index 持久化做幂等。已知局限，属后续方向。
- Watch 断连 60s 释放延迟、Dashboard 部分边界（COMPACTED 展示、percent-encode）等低危项记录备查。

## 5.4 设计取舍与已知局限（诚实版）+ 生产化方向

被问到"这项目还有什么问题"时，**主动、诚实**地说，比被戳穿好十倍。逐条给"承认 + 为什么 + 生产化怎么做"：

| 局限 | 诚实表述 | 生产化方向 |
|---|---|---|
| 无鉴权/TLS | "只面向受信内网/演示；README 已声明。" | 网关注入鉴权或令牌/IP 白名单；TLS |
| `--raft_sync=false` | "压测/演示专用，关了崩溃会丢已提交日志；默认开。" | 生产恒开 + 独立的 WAL/快照盘 |
| apply 非幂等（崩溃重放 revision 漂移） | "当前假设进程崩溃后从快照+日志干净恢复；重放语义未做幂等。" | 持久化 applied index，apply 前查重 |
| AdminService 只能 HTTP | "brpc restful 映射占用 gRPC 路径的设计结果；运维面够用。" | 若要 gRPC：改 `=> Rest` 统一分发或新增方法 |
| Watch 长轮询非流式 | "订阅规模大时实时性/成本不如 gRPC 流。" | 数据面可上 gRPC 流，管理面保留 HTTP |
| LevelDB 单机容量/单写 | "单机存储上限与单写吞吐限制；配置场景够用。" | 大数据量迁移 RocksDB；分片 |
| 线性一致读=Lease | "依赖时钟与 lease 参数；Leader 切换后短暂不可读。" | braft 升级后切 ReadIndex |

> 面试收尾语："我清楚这个项目的边界：它是一个**功能闭环的演示级实现**，面向受信内网；真上生产我第一优先级是鉴权+TLS，然后是 apply 幂等和 ReadIndex 读。"

## 5.5 一套可复用的排查方法论（讲"我怎么调试"时用）

1. **进程管理坑**：Linux 进程名截断为 15 字符 → 二进制 `configraft_server` 的进程名是 `configraft_serv`。清理脚本必须 `pgrep -x configraft_serv`（精确匹配进程名）；在 Claude 这类 agent 环境里 `pgrep -f "configraft_server"` 会误匹配 shell 命令行 wrapper 把自己杀掉。
2. **竞态用压力复现，别指望单步**：closure UAF 只在 `fsync=false` 高吞吐出现，`gdb -batch` 反而改变时序不崩 → 复现要贴近生产负载。
3. **黑盒验证优于人肉推断**：每个修复都配套一个"能稳定复现原 bug 的黑盒操作"（空 key、/status 404、并发写 revision 递增、add_peer 后按版本读配置）。
4. **改动前先留证据**：性能对比要"同环境、同负载、改前改后各跑一遍"；压测原始输出入库（含环境指纹+二进制 md5），可截图证明真实性——这是你简历"数字可信"的底气。
5. **文档化决策**：每个"为什么这么选"落成一篇文档（m5/watch/m6/安全报告…），既是复习材料，也是面试时"我有据可查"的底气。
