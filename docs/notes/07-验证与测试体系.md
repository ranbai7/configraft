# 07 · 验证与测试体系：怎么证明"它是对的"，数字从哪来

> 本章回答面试最常见的两记追问：**"你怎么验证正确性？"** 和 **"你报的数字是怎么测的？"**。含三部分：测试矩阵（47 用例）、混沌测试设计、压测体系与统一口径数字。测试代码在 `tests/`，混沌脚本 `scripts/chaos_test.sh`，压测脚本 `scripts/benchmark.sh`。

---

## 6.1 测试矩阵：47 用例 → 验证点

> ctest 共 4 个测试可执行 = 47 个用例：**store 17 + raft_cas 2 + watch 15 + http 13**。面试被问"你测了什么"，请按"**分层测什么、为什么这么分层**"答，而不是背用例数。

### 为什么这样分层

| 层 | 测试 | 验证什么 | 为什么不放在更上层测 |
|---|---|---|---|
| 存储语义（无网络） | `store_test`（17） | MVCC 读写、revision/version 语义、CAS、Compaction、持久化 | 隔离底层正确性，避免被 Raft 网络掩盖 |
| Raft 一致性 | `raft_cas_test`（2） | **并发 CAS 在真实 Raft 下恰一成功** | 需要真 braft，LocalNode 不能代表集群语义 |
| Watch 语义 | `watch_test`（15） | 重放/过滤/续传/背压/COMPACTED 精确判定 | 逻辑复杂、分支多，宜单测穷举 |
| HTTP 路由集成 | `http_test`（13） | 真拉起 server：REST 分发/CORS/错误码/内置服务/gRPC 共存 | 路由层零测试是审查发现的 U6 缺口，专门补 |

### 6.1.1 store_test 代表性用例（要能报出名字）

- `PutOverwriteIncrementsVersion` / `RevisionMonotonicAcrossKeys`：**revision/version 语义**（覆盖写 version+1；跨 key revision 严格递增）。
- `CasSuccessUpdatesValue` / `CasExpectMismatchNoRevisionConsumed`：CAS **成功推进、失败不消耗 revision**。
- `PersistenceAcrossReopen`：重启后数据仍在（LevelDB 持久化）。
- `ApplyCmdCasEmitsEventOnSuccess / FailedNoEvent`：on_apply 同路径**成功发 PUT 事件、失败无事件**——把"写路径与 Watch 事件耦合"钉死。

### 6.1.2 raft_cas_test：真 braft 组验证原子性

关键设计：**单节点 braft 组**（peers 只填自己 `"127.0.0.1:port"`，多数派=1 自动选主）——为什么不用 LocalNode？文件头注释写明：**LocalNode 是同步直调，测不出"Raft 日志序保证并发原子"这件事**。用例：
- `ConcurrentCasExactlyOneSucceeds`：16 线程同 key 同 expect 并发 CAS → **断言恰 1 个成功**、其余 CAS_FAILED、终值≠旧值。
- `CasFailureDoesNotAdvanceRevision`：8 线程并发只有 1 个赢家 → **全局 revision 只推进 1**。

### 6.1.3 watch_test 代表性用例

- `OverflowBackpressure`：缓冲 2 塞 3 条 → 溢出返回 INTERNAL + 锚点 revision 供续传。
- `CompactedFromRevision`：from=1 < compact_rev=10 → COMPACTED。
- 历史重放含 DELETE、按 key 过滤、开区间 (from, current]、cap 续传、快照加载重置 compact_rev 等。

### 6.1.4 http_test：真拉起 server 的集成测试（U6 补全）

本地起 `ConfigraftServer`（LocalNode 单机、端口 8123），用 brpc HTTP/H2 客户端打真实 `/v1/*` 路由：
healthz / KV 读写删 / 空 key 拒绝(code=6) / batch / CAS / config 发布·版本·回滚 / **层级 key 历史隔离**（前缀碰撞回归）/ watch 返回 current_revision / **CORS 同主机放行·跨站阻断**（H3 回归）/ **内置服务 /status /vars 404**（M7 回归）/ 不支持的方法 / **gRPC 与 HTTP 同端口共存**。

配套工程改进：Compaction 线程 `sleep_for(60s)` 改为 `condition_variable::wait_for`，析构 notify 立即 join（优雅关停，测试多起停必需）。

## 6.2 混沌测试：故障下的正确性验证（`scripts/chaos_test.sh`）

### 6.2.1 场景（4 个，都"杀了真的"）

| 场景 | 手法 | 验证 |
|---|---|---|
| A kill Leader | `kill -9` | 集群自动重选，写不中断/线性一致 |
| B kill Follower | `kill -9` | 多数派仍在，读写正常 |
| C 网络分区 | `kill -STOP` 一个节点（暂停）再 `CONT` 恢复 | **用 STOP 模拟"心跳与请求全不可达"**（无需 root，iptables 分区要 root） |
| D 重启追赶 | 重启宕机节点 | 节点经日志/快照自动追平，Watch 补上断档 |

### 6.2.2 两个后台 verifier（核心：怎么"断言"没出错）

```
writer:       写 "key = 值(严格递增序号)" → 立刻读
               读到空 / 读到 < 上次确认值   → 记 LINEAL_VIOLATION(线性一致违例)
watch_verifier: 带 from_revision 长轮询续传, 逐事件校验
               revision 必须严格 > 上一个   → 否则记 WATCH_ORDER_VIOLATION(乱序/重复)
```

跑完全部场景后 grep 计数，**违例数 = 0** 脚本才 exit 0。Leader 探测走 `/healthz` 的 `"role":"leader"`，定位进程用 `ss -tlnp`。

> **诚实边界（面试主动说，加分）**："我的 verifier 是'写后立即读同连接'的黑盒定向校验——它能抓出读旧值/乱序/丢事件这类大问题，但**不是** Jepsen/Knossos 那种记录全部并发历史、做严格线性化判定的 checker。真要严格证明，业界做法是 Jepsen + 完整历史记录离线分析。我清楚这个工具的定位。"

## 6.3 压测体系与统一口径数字

### 6.3.1 环境与方法（报数字前先报这个，可信度翻倍）

> 阿里云云主机 · **8 vCPU / 16G / NVMe SSD / Ubuntu 22.04** · 多节点进程**同机环回** · **ghz**(gRPC) + **wrk**(HTTP) · 每项 **10s** · 数据为**审查加固后当前代码**实测（commit e5d737b）。

指标格式 `QPS / P99(ms)`：gRPC 按 ×8 / ×64 / ×128 并发，HTTP 固定 100 连接。复现：`bash scripts/benchmark.sh --all --dur 10`。

### 6.3.2 主表（8 核云实测，README 口径）

| 场景 | 3 节点·默认持久化 | 3 节点·关 fsync | 5 节点·默认持久化 |
|---|---|---|---|
| gRPC 写 Put ×8 | 1.8k / 10.3 | 15.9k / 1.4 | 1.2k / 11.0 |
| gRPC 写 Put ×64 | 10.0k / 11.6 | 28.2k / 4.7 | 7.4k / 14.7 |
| gRPC 写 Put ×128 | 16.0k / 13.0 | 31.0k / 7.1 | 12.6k / 18.9 |
| gRPC 读 Get ×64 | 45.2k / 2.8 | 42.5k / 3.3 | 44.1k / 3.0 |
| HTTP 读 GET | **275k / 0.5** | 271k / 0.5 | 267k / 0.5 |
| HTTP 写 POST | 17.9k / 12.6 | 75.4k / 4.2 | 13.0k / 15.5 |

> 完整矩阵（含单机、5 节点关 fsync、P99 长尾说明）见 README「性能与验证」与 `../性能压测报告.md`。原始证据（环境指纹 + 二进制 md5 + 逐项 stdout）在 `../压测结果_云主机_20260820.txt`。

### 6.3.3 四条可背诵结论

1. **读远高于写**：HTTP 读 25–30 万 vs 写 1.2k–31k——符合配置中心"读多写少"形态。
2. **Raft 规模代价**：5 节点比 3 节点写降 **15–32%**（多数派 2/3→3/5），读几乎不受影响；代价换来容错 1→2 故障。
3. **fsync 是写最大开销**：开/关差 **8–10 倍**——强一致+崩溃不丢的固有代价。
4. **写路径峰值**（8 核上限）：单机 ~38k / 3 节点关 fsync ~31k / 5 节点关 fsync ~27k QPS（×64→×128 已趋饱和）。

### 6.3.4 "简历写 10k QPS"的口径核对（别被问穿）

简历那行"集群 gRPC 写 10k QPS(P99 12ms, fsync 开启)" = **3 节点、gRPC Put ×64、默认持久化** 那格（10.0k / 11.6）。×128 能到 16k 但 P99 升到 13.0ms。被问"为什么写 10k 不写 16k"→ 答："10k 是 ×64 更稳的口径、P99 ~12ms；×128 到 16k 是峰值、P99 略涨，且这是同机环回压的，我留了余量。" **主动把环境+并发讲清，数字就不像吹的。**

### 6.3.5 加固零回退（审查的"买单"）

shared_mutex 修复 UAF（H1）后同环境复测完整矩阵：**集群写路径差异全部 ±5% 内、读完全不受影响**。结论：**共享锁修 UAF 是零性能代价的**——这是"工程加固 vs 性能"的黄金论据（README §6、`../性能压测报告.md` §6）。
