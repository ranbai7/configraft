## 7.1 高频问答（按主题，答案即"说人话版"）

### A. 项目总述 / 架构

**Q1 用 30 秒介绍一下这个项目。**
A：对标 etcd 的分布式配置中心，解决微服务配置"集中管理、实时生效、可一键回滚"。架构四层：API 层（brpc 单端口 gRPC+HTTP）→ 复制状态机（braft）→ Raft 层 → MVCC on LevelDB。三个卖点：Raft 强一致 + **Lease 线性一致读**（braft v1.1.2 没有 ReadIndex，我用 lease 自研）；**MVCC 多版本**支持回滚/历史/审计；**HTTP 长轮询 Watch** 有序不丢。（00）

**Q2 为什么不直接用 etcd / 为什么用 braft？**
A：这是 C++ 技术栈下的复刻练习；etcd 是 Go + 自有 Raft。选 braft = 工业级 C++ Raft 实现，省去从零实现共识的正确性风险，把精力放在业务语义（MVCC/Watch/CAS）与工程验证上。（00）

**Q3 系统里有哪几个抽象/关键类？画一下依赖关系。**
A：`ConfigNode`（服务层唯一依赖）→ `RaftNode`/`LocalNode` → `ConfigraftStateMachine`(on_apply) → `Store`(LevelDB) + `WatchHub`(广播)。Server 组装见 03。（00/03）

### B. 一致性与 Raft（最高频）

**Q4 写路径怎么保证一致？**
A：所有写 = 一条 RaftCmd 进复制日志，多数派确认后 `on_apply` 在 Leader **串行**落库；Follower 也从日志 apply 同序日志 → 各副本状态相同。同一批写（数据+revision）用 LevelDB WriteBatch 原子提交。（04）

**Q5 为什么不能"主从异步复制"要共识？**
A：异步复制在主故障时可能丢最后的写，甚至脑裂双主。Raft 把提交定义为"多数派确认"，多数派两两相交 → 任意时刻最多一个能提交 → 安全。（01）

**Q6 Leader 直接读本地状态机为什么不够线性一致？**
A：两个滞后场景——①Leader 可能**不知道**自己已被赶下台（网络孤岛）还服务读，而新 Leader 可能已提交新写；②即使仍是 Leader，本地状态机可能还没 apply 完**已提交**的日志（刚当选/刚恢复）。本地读会漏掉此前已确认的写。（01/04）

**Q7 那你读怎么保证线性一致？（核心题，务必层层讲）**
A：三步：IsLeader 校验 → **WaitLeaderLease**（等 braft lease VALID）→ **WaitAppliedCatchUp**（等 applied≥commit）→ 本地读。论证：lease VALID ⟹ 本任期 no-op 已提交（Leader Completeness ⇒ 旧任期已提交写都在我日志里）且我是唯一 Leader；catchup ⟹ 把它们 apply 进状态机；∴ 本地读状态 ≥ 一切此前已提交的写。读失败宁可拒绝也不返回过期值。（04）

**Q8 为什么不用 ReadIndex？**
A：braft v1.1.2 没有暴露 ReadIndex API（源码确认）。ReadIndex 每次读要一次多数派确认 RPC，Lease 是零 RPC 纯本地读，吞吐更高；代价是依赖时钟、Leader 切换后有不可读窗口。有 ReadIndex 我会更倾向它。（01/04）

**Q9 lease 是什么？为什么所有节点必须开？**
A：lease 靠多数派周期性确认续租，VALID = 最近与多数派有交互。开启后 **Follower 在 lease 内不投给更高任期候选**——这保证"lease 有效期内没有我不知道的新 Leader"。若只有 Leader 开、Follower 不开，脑裂后可能选出第二个 Leader，读到过期值。server_main 在解析参数后强制开启，防命令行覆盖。（01/04）

**Q10 为什么新 Leader 要先提交 no-op？**
A：表面是"推 commitIndex 越过旧任期日志"，本质靠 Leader Completeness 保证旧任期已提交写进入新 Leader 日志 → 一致读与后续提交的前提。（01）

**Q11 expected_term 是干嘛的？**
A：braft apply 是异步的；提交完成时本节点可能已不是当初那个任期的 Leader。expected_term 不匹配则拒绝该条 → 防止旧任期日志被当新任期写入（ABA）。（04）

**Q12 读会阻塞写吗？会拖慢吗？**
A：不会。读是本地 Store 共享锁读；写阻塞在 braft 复制层。Lease 读让读几乎免费 → 读 27 万 QPS、写 10k QPS。（04/07）

### C. MVCC / 存储

**Q13 revision 和 version 什么区别？**
A：revision 全局单调（每写+1），version 单 key 计数（从1）。revision 是 MVCC/Watch/CAS/Compaction 的共同锚点；version 是配置"第几版"，回滚的目标参数。（02/05）

**Q14 为什么删除要写 tombstone 而不是物理删？**
A：保持 Raft 日志 append-only 与 MVCC 历史完整；tombstone 是主索引里 `deleted=true` 的一条空 KV，Get 视为不存在。回滚语义、审计都依赖历史不删。（05）

**Q15 回滚怎么实现？为什么不直接指回旧版本？**
A：读目标版本的值 → 再发布一次产生**新版本**（不删历史）。Raft 日志不可改写，etcd 也是"写回旧值"语义；历史是不可变事实。（05）

**Q16 CAS 原子性从哪来？失败消耗 revision 吗？**
A：CAS 是一条 RaftCmd，在 on_apply **串行**执行 → 无需锁。失败直接返回 CAS_FAILED，**不消耗 revision**（没写任何东西）。`expect=""` = 期望 key 不存在（含 tombstone）。并发 N 个 CAS 恰一成功由 raft_cas_test 验证。（04/05/07）

**Q17 历史无限增长怎么办？**
A：后台线程每 60s 对每 key 保留最近 10 版，删除 v/ 与 cfg/ 记录，并把删掉的最大 rev 记为 `compact_rev` 水位（与删除同 WriteBatch 原子）。客户端用被回收的 from_revision 续传 → COMPACTED，从新锚点重建。（05）

**Q18 为什么 revision 递增和数据写要同一个 WriteBatch？**
A：分开写会出"revision 推进了但记录没落"的半提交 → 节点发散。合批后要么全生效要么全不生效。（05/06）

### D. Watch

**Q19 Watch 怎么保证有序不丢可续传？**
A：事件带全局单调 revision；客户端用响应里的 `current_revision` 当下次 `from_revision`。有事件时锚点 = 最后一条事件的 rev（不是 store 当前值，防漏掉最后事件之后的新写）。（05）

**Q20 历史事件从哪来？要额外持久化吗？**
A：不用。事件可随时从 MVCC 的 `v/` 记录**重放**（revision 保序编码 + Seek）。实时事件走 WatchHub 广播。（05）

**Q21 慢消费者怎么办？为什么断开而不是无限缓冲？**
A：每订阅者缓冲上限 1024；满了置 overflow 断开，返回 INTERNAL + 锚点让客户端重放补齐。无限缓冲=内存膨胀+事件陈旧；直接丢=静默丢事件。关键是**绝不阻塞 on_apply**。（05）

**Q22 Watch 能挂 Follower 吗？落后怎么办？**
A：能。Follower 也在 on_apply 后 Broadcast。若本地落后于 from_revision，先等追平 ≤5s，超时返回 INTERNAL 保留锚点重试——防重放旧事件造成重复。（05）

**Q23 什么时候返回 COMPACTED？**
A：from_revision > 0 且 `compact_rev > from_revision`（历史被回收），快速路径 + 重放内双重判定，响应带 current_revision 供重建。（05）

### E. brpc / bthread / 工程

**Q24 brpc 一个端口怎么跑 gRPC + HTTP + Raft？**
A：brpc 单端口按首字节识别多协议；braft 的 Raft service 与业务 service 挂到同一 brpc Server。（03）

**Q25 在 brpc 里写"会等待"的代码要注意什么？**
A：用 bthread 原语（bthread::Mutex/cv），别用 std::cv——bthread 阻塞在 std 同步上会占死底层 pthread worker（num_threads=4），高并发下假死。真实踩过并修复。（02/04/06）

**Q26 你压测报的数字怎么测的？可复现吗？**
A：环境 8 核/同机环回/ghz+wrk/每项 10s；`benchmark.sh --all --dur 10` 一键复现；原始证据（环境指纹+md5）入库。报告前先报环境，数字才可信。（07）

**Q27 代码审查发现的最大问题是什么？**
A：H1 快照安装 UAF——LoadSnapshot 会 reset LevelDB 指针，与并发读/Compaction 无同步即悬垂。用 shared_mutex：重建持独占锁、访问持共享锁，并拆 *Locked 防 shared_mutex 不可重入。修完同环境复测零回退。（06）

**Q28 项目有什么局限？生产化第一步做什么？**
A：无鉴权/TLS（面向受信内网，README 已声明）；apply 非幂等（崩溃重放 revision 漂移）；读=Lease 依赖时钟。生产化第一优先级：鉴权+TLS，然后 apply 幂等、braft 升级后切 ReadIndex。（06）

## 7.3 简历逐条应答脚本（对应你简历五条）

> 简历一句话 → **30 秒主答**（主动讲），面试官若深挖再放 **弹药**。

### ① "基于 braft 3 节点强一致集群 + 无 ReadIndex 故用 leader lease 自研线性一致读 + 混沌测试"
- **30s 主答**：写走 Raft 日志多数派提交、on_apply 串行落库天然一致；读是最难点——braft v1.1.2 没有 ReadIndex，我利用它内置 leader lease：lease VALID（no-op 已提交+我是唯一 Leader）再等 applied≥commit 后本地读，杜绝过期读；并用 kill Leader/网络分区/重启的混沌测试验证写线性一致、Watch 有序不丢。
- **弹药**：Q6/Q7/Q8/Q9/Q10 + 04 章证明链 + 07 章混沌（含诚实边界）。

### ② "MVCC 多版本 + 全局 revision + 一键回滚 + Compaction"
- **30s 主答**：LevelDB 上自己排布 k/主索引、v/{rev}/{key} 历史、cfg/版本索引、meta/revision 时钟；revision 用 16 位 hex 编码使磁盘序=时间序，历史/回滚/Compaction/Watch 全复用。回滚=写回旧值产生新版本（etcd 语义）。后台每 key 保留 10 版，回收水位 compact_rev 与删除同批原子提交。
- **弹药**：Q13~Q18 + 05 章（Key 布局、锁模型、*Locked）。

### ③ "HTTP 长轮询 Watch：revision 断点续传有序不丢，慢消费者溢出即断开、凭锚点重连重放"
- **30s 主答**：WatchHub 单实例，事件只在 on_apply 落库后广播（Leader/Follower 都推，可挂任意节点）；历史从 MVCC v/ 记录重放不需额外持久化；锚点=最后一条事件 rev 保证不丢；每订阅者缓冲 1024，满了断开+INTERNAL+锚点，客户端重放补齐，绝不阻塞写路径。
- **弹药**：Q19~Q23 + 05 章 3.4。

### ④ "brpc 单端口承载 gRPC + HTTP + Raft；在线成员变更、新节点快照追赶；Docker 一键 3 节点；GitHub Actions CI"
- **30s 主答**：靠 brpc 单端口多协议 + braft::add_service 共享端口；restful 映射有坑（不支持方法前缀、具体方法映射会占用 gRPC 路径），所以业务服务用 Rest 统一分发、Admin 纯 HTTP；成员变更封装 braft add/remove，移除 leader 自动让位，新节点先追平数据再入集群；部署踩过进程名截断、str2endpoint 只认 IP 的坑。
- **弹药**：03 章全章 + 05 章 3.8 + 06 章 5.5 方法论。

### ⑤ "8 核 16G 压测：HTTP 读 27 万 QPS、集群 gRPC 写 10k(P99 12ms,fsync 开)；审查修复 9 项缺陷，加固后零回退"
- **30s 主答**：先报环境再报数——8 核/同机环回/ghz+wrk/每项10s/加固后代码。主表关键格：读 275k、写 ×64=10k(P99 11.6)、关 fsync 快 8-10 倍、5 节点降 15-32%。审查 9 项里最高危是快照 UAF 和 CORS 通配；用 shared_mutex 修 UAF 后同环境复测差异 ±5% 内——零性能回退。
- **弹药**：Q26/Q27 + 07 章 6.3 + 06 章 5.3（9 项表）。

## 7.4 一页速记卡（面试前最后一小时）

### 一句话定位
对标 etcd 的 C++ 分布式配置中心：Raft(braft) 强一致 + MVCC 多版本可回滚 + HTTP 长轮询 Watch，brpc 单端口 gRPC+HTTP+Raft。

### 关键数字
| 项 | 值 |
|---|---|
| HTTP 读 / 集群写(×64, fsync开) / 关fsync | 275k QPS / 10.0k / 28.2k |
| 5 节点 vs 3 节点写 | -15~32% |
| fsync 开关差 | 8–10 倍 |
| 加固零回退 | 全部 ±5% 内 |
| 测试 | 47 用例 = store17 + raft_cas2 + watch15 + http13 |
| Watch 缓冲 / 保留版本 / 回收周期 | 1024 / 10 / 60s |
| 一致性读窗口 / 追平上限 / election | lease ≤1s / catchup ≤1s / 1000ms |

### 关键论证链（口述一遍）
**线性一致读** = IsLeader → **lease VALID**(no-op 已提交 ⇒ Leader Completeness ⇒ 旧任期已提交写都在日志；唯一 Leader) → **applied≥commit**(写进状态机) → 本地读。宁可拒绝不给过期值。

### 关键设计（一句话每条）
- **写** = RaftCmd 进日志 → on_apply 串行 → WriteBatch(数据+revision) 原子。
- **回滚** = 写回旧值成新版本（append-only）。
- **CAS** = 一条日志串行执行，失败不消耗 revision。
- **Watch 锚点** = 有事件时用"最后一条事件 rev"。
- **背压** = 满了断开 + 返回锚点重连。
- **bthread** = 等待必须用 bthread 原语（std::cv 占死 worker）。
- **锁** = shared_mutex 重建独占/访问共享 + *Locked 防重入。

### 九个修复编号（H=高危）
H1 快照UAF / H2 单机并发写revision重复 / H3 CORS通配 · M1 快照revision原子 / M2 快照缺cfg索引 / M3 层级key前缀碰撞 / M4 revision原子提交 / M5 空key / M7 内置服务面板关闭。
