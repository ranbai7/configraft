# Configraft 项目分析笔记 · 学习导航

> **目标读者**：本项目源码的读者与维护者。
> **这套笔记要解决一件事**：把 Configraft（对标 etcd 的分布式配置中心）**从"用了 braft 做了个配置中心"讲到"为什么这么设计、正确性怎么证明、踩过哪些坑、数字怎么来的"**——读完能完整复述这个系统的设计取舍。
> **定位**：整合重写 + 定点补缺。吸收仓库内既有高质文档（`../watch.md`、`../m5.md`、`../raft-and-braft.md`、`../安全审查报告.md`、`../性能压测报告.md`），补充缺失的 **bthread 运行模型 / 全链路时序 / 存储 MVCC 深讲 / 集中式 FAQ / 速查卡**。旧文档一律不改，本文档只在文末给延伸链接。

## 一、这套笔记怎么学（三层学习法）

读懂一个后端项目，**"理解 → 表达 → 应变"**三件事缺一不可。笔记内容对应用三种用法：

| 层 | 动作 | 对应材料 | 检验标准 |
|---|---|---|---|
| **第 1 层 · 通读理解** | 按 00 → 08 顺序完整读一遍，边读边对照源码 | 全文 | 每个"为什么"你都能复述出理由 |
| **第 2 层 · 合书复述** | 不看笔记，把每章"主干问题"讲给自己/别人听 | 每章末尾的【自查】 | 30 秒能讲清一个特性"是什么/为什么/怎么实现" |
| **第 3 层 · 脱稿自讲** | 手画时序图 + 记数字 + 应对提问 | `08-高频问答` 第 7.2 手画题 + 7.4 速查卡 | 能连续讲 30 分钟不卡壳 |

> 检验是否真正理解一个系统，最有效的一招是**在某个细节上连着往下问 3 层**（"为什么"→"那如果…怎么办"→"代码里哪一行"）。所以笔记里所有结论都尽量给到 **源码位置**（形如 `src/raft/raft_node.cpp:166`），复习到第 2 层时请把这些位置也记住。

## 二、你最好先具备的前置知识

这套笔记假设你已经会（或边看边补）：

- **C++ 基础**：RAII、`std::shared_mutex`、`std::mutex`、protobuf 基本用法、回调/闭包。
- **计算机网络**：HTTP 长轮询、gRPC(HTTP/2)、端口与进程模型常识。
- **操作系统**：fsync 与落盘、进程/线程、`kill -9`/`SIGSTOP` 语义。
- **分布式入门直觉**：CAP、为什么多副本会不一致（不需要精通，第 01 章会带）。

> 真薄弱的部分不用慌：`01`/`02` 两章就是按"重点驱动、核心的讲透"来写的，够用为止；想更深入去翻文末延伸文档。

## 四、全文统一约定（重要）

1. **路径**：`src/xxx` 均相对项目根 `configraft/`。代码引用形如 `raft_node.cpp:166` 表示 `src/raft/raft_node.cpp` 第 166 行附近。复习请以**真实源码为准**——如行号有漂移，用你本地的源码为准，本笔记行号是撰写时的快照。
2. **数字口径**：性能数字一律以 **`../性能压测报告.md`（2026-08 阿里云 8 核实测、审查加固后）** 为准，不混用 m7 的 4 核 VM 旧数据。
3. **术语**：
   - `revision` = 全局逻辑时钟（每写 +1，跨 key 单调），Watch/CAS/MVCC 的共同锚点。
   - `version` = 单个 key 的修改序号（从 1 起），配置发布/回滚看它。
   - `commit_index` / `applied_index` = braft 的已提交 / 已应用日志下标。
4. **代码引用只为定位讲解，本笔记不含大段源码**：贴的都是"伪代码 + 关键判断"，防止你背代码；真要看实现，按引用去翻。

## 六、勘误记录（2026-09-30 全文核对）

> 对 9 篇笔记做了一轮**逐条对源码核对**（约 400 处事实性陈述，分 4 组并行核对 + 交叉复核）。以下是有出入并已修正的条目，留档便于复查。

**① Raft 选举（01 章，最主要的一处）**

| 原文 | 真实情况 |
|---|---|
| "Follower 随机化（如 **150–300ms**）的计时器" | 那是教科书通用值。**本项目是 [1000, 2000] ms**，基准 1000 + 抖动 ≤1000，**第一次调度就已随机** |
| "Follower 超时 → **term+1 转 Candidate** → 先投自己" | 漏了 **pre-vote**：超时后先预投票（**term 不变**），拿到多数派**才** term+1 转 Candidate 并自投 |
| "Leader 挂了约几秒内自动选出" | 补实测：`kill -9` → 约 **2.17 s**，term **2→3**；首次选举 init→发起 **1010~1512 ms** |
| "3 节点集群总是从 term=2 开始" 因为"**首轮 split vote，第二次超时才选出**" | **不是**。真实因果：节点初始 term=**1** → pre-vote 不推进 term → `elect_self` 时 +1 → **一轮就落在 term 2**。实测 14/14 次 term=2，其中 13 次只有一个节点超时、根本无竞争 |

新增内容：与教科书的偏差对照表、**实测时间参数表**（选举超时/心跳 100ms/Follower Lease 2000ms/初始 term=1）、启动 vs 重选对比、"选举超时 vs Follower Lease 不重复"的反证、**braft 里两个 lease 对象**的区分。

**② 其它已修正条目**

| 位置 | 原文 | 修正为 |
|---|---|---|
| 00 章 | "`on_apply` 只在 **Leader 本机**执行" | **每个副本都执行**；Leader 独有的只是"带回执、能唤醒本地等待者" |
| 04 章 | "不是 Leader 但 lease 没就绪 → 返回 INTERNAL" | **是 Leader 但 lease 未就绪**才回 `INTERNAL`；不是 Leader 回 `NOT_LEADER`+真实 `LeaderId()` |
| 04 章 | "`Finish(result)` 唤醒等待者" | `Finish` 只填结果；**`Run()` 才唤醒**（由 `AsyncClosureGuard` 在独立 bthread 触发） |
| 04 章 | wait 顺序 "Finish → 客户端响应 → Broadcast" | 实际 **Broadcast 在前**、Finish 在后 |
| 04 章 | "`WaitState` 里存结果，靠它安全读结果" | `WaitState` 只有 `mu/cv/done`；结果是 closure 的 `out_`，指向调用方自己的对象 |
| 03 章 | 配置读写"本地（**经 lease**）" | **纯本地读，不做 lease 校验**；全项目调 `WaitLeaderLease` 的只有 `Get(serializable=false)` 一处 |
| 03 章 | "`--node`/`--peers` 非空则建 RaftNode" | 判据**只有 `--node`**；`--peers` 单独非空仍是 LocalNode |
| 03 章 | "声明在前 ⇒ 析构逆序**先销毁**" | 说反了：声明在前 ⇒ 逆序**后**销毁（正是为了让 hub 比 node 活得久） |
| 02 章 | "扫 `v/` 前缀做 MVCC 历史查询" | `v/` 供 **Watch 重放 / Compaction**；**GetHistory 扫的是 `cfg/{key}/{ver}`** |
| 02 章 | "被回收历史 → GetHistory 返回 `VERSION_NOT_FOUND`" | `GetHistory` 返回 `void`、不出码；`VERSION_NOT_FOUND` 来自 **`GetConfig(key,version)`** |
| 02 章 | bthread cv "是正确且足够快的方案" | 补上取舍：4 核 c8 下 **2912 vs std::cv 7813 QPS，慢约 3 倍**，是"用吞吐换正确性"的显式取舍 |
| 05 章 | "锁序：`hub_mu_` → waiter->mu" | 成员名是 **`WatchHub::mu_`**（无 `hub_mu_` 这个成员） |
| 06 章 | 把 `d5b0f9e`（落后节点重放旧事件）归到 **M4** | 该 commit 是 **`fix(M7)`**，应是 M7（混沌脚本 M7 才搭起来） |
| 07 章 | 校验器叫 **`writer`** | 脚本里是 **`verifier`** |
| 07 章 | "写后立即读**同连接**" | 是**两次独立 HTTP 请求**，不是同一条连接 |

**③ 两处"口径"问题（同一说法曾散布在 README / 压测报告 / CLAUDE.md / 笔记，现已全仓统一）**

| 旧说法 | 问题 | **统一后的口径（全仓已改）** |
|---|---|---|
| "fsync 开/关差 **8–10 倍**"（有时举 ×64 的 10.0k→28.2k 为例） | ×64 那格实际只有 **2.8 倍**，自相矛盾。8–10 倍只成立于**低并发 c8** | "**低并发(c8) 下差 8–10 倍**；×64 约 2.8 倍、×128 约 1.9 倍"——**报倍数必带并发度** |
| "加固后集群写路径差异**全部在 ±5% 内**" | 报告自己的对比表里 `HTTP 写 POST·关 fsync` 是 70.7k→75.4k（**+7%**） | 结论**零回退成立**，上界改说"**无一项回退，最大单格 +7%（且是变快）**" |
