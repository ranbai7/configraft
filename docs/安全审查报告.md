# Configraft 代码安全审查报告

> **审查时间**：2026-08-20
> **范围**：全项目（Raft 核心 / 服务层与协议 / 存储与 Watch / 前端与测试）
> **方法**：4 个并行独立审查（子代理交叉验证），仅保留置信度 ≥ 8/10 的发现
> **结论**：发现 **3 项 HIGH + 多项 MEDIUM**。HIGH 全部修复（commit `e5d737b`），MEDIUM 中"正确性+安全核心"9 项已修复，其余未修项与设计取舍记录如下。
>
> 本报告既可作为工程文档，也可作面试素材（讲解"发现问题 → 权衡取舍 → 修复"的完整过程）。

## 1. 已修复项（9 项，commit e5d737b）

| # | 严重度 | 问题 | 修复 |
|---|---|---|---|
| H1 | HIGH | `Store::LoadSnapshot` 直接 `db_.reset()`，与并发读/Compaction 无同步 → use-after-free | `db_mu_` 共享互斥量：重建 DB 持写锁，读/写/Compaction/快照导出持读锁 |
| H2 | HIGH | 单机模式 `LocalNode::Apply` 无锁并发写 → `NextRevision` 读-改-写非原子，revision 重复 | `LocalNode::Apply` 加互斥锁，写路径串行（等价集群 on_apply） |
| H3 | HIGH | 通配 `Access-Control-Allow-Origin: *` + 无鉴权 → 任意网页可跨站读写配置/成员 | 收紧为仅同主机跨端口回显 Origin（`rest_util.h::IsAllowedOrigin`） |
| M1 | MEDIUM | 快照 revision 在 LevelDB snapshot 之外读取 → 跨节点 revision 编号发散 | `Store::ExportSnapshot` 在单个 snapshot 内读 revision + 数据 |
| M2 | MEDIUM | 快照不含 `cfg/` 配置版本索引 → 新节点按版本读配置丢失 | `SnapshotData` 加 `cfg_kvs` 字段，导出/恢复 cfg/ 索引 |

## 2. 未修复项

> 分级说明：
> - **重要**：真实风险 / 正确性缺口，因改动范围大、语义需权衡或需新增配置而未在本次范围修复，建议后续处理。
> - **设计取舍**：文档化的有意选择，非缺陷，面试可主动讲解。
> - **低优先加固**：防御纵深 / 边界健壮性，影响有限。

### 2.1 重要（建议后续处理）

#### U1. 全部接口无鉴权；`/addpeer` 可把攻击者节点加入集群（数据外泄通道）
- **严重度**：HIGH（若绑定非 localhost；默认 127.0.0.1 时降级）
- **位置**：`src/server/admin_service_impl.cpp:32-60`、`src/server/server.cpp:106-113`、`proto/configraft.proto:133-137`
- **问题**：所有管理/写接口无任何认证。`POST /addpeer {"peer":"attacker:9999"}` 可把攻击者控制的节点加为 Raft 成员，Leader 随后会把**完整快照 + 日志**复制给它 = 数据外泄通道；`RemovePeer` 可破坏可用性。`docker-compose.yml` 把 `8001:8001` 直出宿主机，边界完全依赖网络隔离。
- **已缓解**：CORS 已收紧（浏览器跨站向量已堵），但非浏览器客户端（curl/脚本）仍可直连。
- **为何未修**：需引入令牌鉴权或 IP 白名单，属新增配置面，用户本次未选"全面修复"范围。
- **建议**：生产/云部署至少加共享令牌（请求头校验）或 IP allowlist；README 明确"信任所在网络"的安全模型。

#### U2. on_apply 非幂等：崩溃重启无近期快照时整段重放已提交日志 → revision/version 漂移
- **严重度**：MEDIUM | 置信度 7/10
- **位置**：`src/raft/state_machine.cpp:16-51`
- **问题**：已核实 braft applied index **只存内存不持久化**（重启 `_last_applied_index=0`）。若崩溃在两次快照（`snapshot_interval_s=30`）之间，重启会从日志第一条起重放已提交日志：revision/version 双倍递增、产生重复 `v/` 记录、重复广播 Watch 事件 → 与其它副本 revision 永久漂移（值因写入幂等仍一致）。
- **为何未修**：修复需在 Store 的 WriteBatch 里持久化"已应用日志 index"并在 on_apply 跳过 `index <= last_applied` 的条目，改动跨 store/state_machine 且需与 braft 日志序对齐，属较大语义改动。
- **建议**：在 meta 里持久化 last_applied_index，on_apply 前判重跳过。**面试可讲**：braft 与业务状态机的幂等约定。

#### U3. Watch 断连资源释放延迟 + 并发订阅无上限
- **严重度**：MEDIUM（resource-exhaustion 类）
- **位置**：`src/watch/watch_hub.cpp:179-191`、`watch_service_impl.cpp:57-61`
- **问题**：`canceled`（`cntl->IsCanceled()`）只在 cv 被唤醒时轮询，客户端断连不主动唤醒 → 断连的 Waiter 与阻塞 bthread 最长滞留 60s；`max_concurrency=0` 无订阅上限，批量"连上即断"可造成 Waiter 堆积。
- **为何未修**：属可用性/资源类，非数据正确性。
- **建议**：`cntl->NotifyOnCancel` 在断连时主动唤醒 cv；对并发 waiters 设上限。

#### U4. 单机模式（LocalNode）Dashboard 整体不可用 / 非 Leader 落地节点列表空
- **严重度**：MEDIUM
- **位置**：`src/raft/local_node.h:32-37`（`Role()="leader"`、`LeaderId()=""`、`Peers()={}`）、`web/app.js:35-55`
- **问题**：① 单机模式 `leader_id` 为空 → 所有操作报"未发现 Leader"、节点列表空；② 集群模式若用户在非 Leader（8002/8003）打开 Dashboard，`Peers()` 依赖 `list_peers()`（仅 Leader 返回成员）→ 节点列表永远"获取中"。Dashboard 实际只对"Leader 视角 + 集群模式"自洽。
- **为何未修**：属前端体验缺陷，非正确性；`list_peers` 行为是 braft 限制。
- **建议**：前端 `discover()` 在 peers 为空且已知 leader_id 时向 Leader 再查一次 `/healthz` 兜底；LocalNode 对单机模式返回自身为 leader。

#### U5. HTTP 侧 key 百分号编码后端不解码 → 与 gRPC 的 key 身份不一致
- **严重度**：MEDIUM | 置信度 8/10
- **位置**：`web/app.js:129`（`encodeURIComponent(key)`）、`src/server/rest_util.h:19-27`（直接用 `unresolved_path`，已核实 brpc URI 解析不做 `%` 解码）
- **问题**：key 含空格/`%`/`/` 等特殊字符时，前端编码为 `a%20b`，服务端原样存 `a%20b`；而 gRPC 客户端写 `a b` 是另一个 key → 同一逻辑 key 跨协议分裂。普通 key（如 `gateway.rate_limit`）不受影响。
- **建议**：后端统一对 `unresolved_path` 做百分号解码，或前端与后端约定一致的编码规则。

#### U6. HTTP/RESTful 路由层零测试
- **严重度**：MEDIUM | 置信度 9/10
- **位置**：`tests/`（三个测试全走 C++ 直调，无任何经 brpc Server 打真实 HTTP 的测试）
- **问题**：`/v1/kv/*` 路由、CORS 预检、json2pb body 解析、restful 匹配这类最易出错的接线层完全裸露——本次审查的 H3（CORS）、U5（编码）正发生在这层。
- **建议**：补一个拉起 `ConfigraftServer`（或单端口 brpc）的 HTTP 集成测试：GET/POST/DELETE + OPTIONS 预检断言。

### 2.2 设计取舍（文档化，非缺陷）

| # | 项 | 说明 | 面试讲解点 |

| D1 | Watch 缓冲溢出断开 | 慢消费者溢出 → 清缓冲 + 返回 `INTERNAL` + `current_revision` 锚点供重连重放（`watch_hub.cpp:197-203`） | "缓冲上限 → 断开 → 锚点续传"背压闭环 |

## 3. 面试讲解建议

- **已修复项的讲法**：以 H1/H2/M4 为主线——"Store 的并发边界没有与『写串行、读并行』假设对齐"：① 快照安装与并发读竞争 db_ 生命周期（shared_mutex 拆 *Locked 防锁重入）；② 单机模式踩穿"仅 on_apply 串行"约定（Apply 加锁）；③ meta/revision 与业务写分提交易导致状态发散（并入 WriteBatch 原子提交）。
- **未修项的讲法**：U1（无鉴权）主动说明取舍——"默认信任内网，CORS 已堵浏览器跨站，若生产暴露需加令牌/IP 白名单"；U2（幂等）可讲 braft applied index 不持久化的坑。
- **设计取舍的讲法**：D1（Watch 背压）、D4（双协议取舍）是能展示工程判断的点。
