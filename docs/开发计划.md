# Configraft 项目开发计划

> **目标读者**：本人。用途：项目开发的唯一导航——防止偏离方向、保证每个阶段都在为"找到 C++ 后端岗位"累积真实的面试资本。
> **配套文档**：`项目概述_审查后.md`（架构与技术栈权威定义）、`README.md`（对外展示）。

---

## 一、项目锚点（防偏离原则，所有决策回到这里）

**一句话定位**：基于 Raft 共识的分布式配置中心——把服务配置集中存储，做到**强一致、实时生效、可回滚**。

**技术核心**：在百度工业级 Raft 库 **braft** 之上，亲手设计并实现一个完整的配置存储系统（MVCC 版本、回滚、CAS、Watch 实时推送、Compaction、一致读）。

**明确的边界**：

| ✅ 要做（项目深度所在） | ❌ 不做（防跑偏） |
|---|---|
| 复制状态机应用层：MVCC / 版本 / 回滚 / CAS / Watch / Compaction | ❌ 自研 Raft 算法（时间黑洞，深度靠读 braft 源码补） |
| 协议与 API 设计：gRPC + HTTP 双协议、Proto、错误码、路由 | ❌ 自研存储引擎（用 LevelDB，深度靠理解 LSM-Tree 补） |
| 一致性语义：ReadIndex 线性一致读、Watch 断点续传 | ❌ 引入重型中间件堆功能（Redis/MQ 等与本题无关的组件） |
| 工程化：Docker 集群、CI、压测、混沌测试、性能调优 | ❌ 为"炫技"加花哨功能（每个功能必须能服务"讲清配置中心"） |

**北极星指标（做完 = 达到这三条）**：

1. **能连续讲解 30 分钟**：对每个模块都能答出"为什么这么设计"，而不是"这是 braft 提供的"。
2. **能回应深挖**：Raft 原理、LevelDB 原理、一致性模型、压测数据，被追问三层不崩。
3. **有可展示的证据**：运行中的 3 节点集群 + 压测报告 + 混沌测试记录 + 源码阅读笔记（放 repo）。

> **防偏离检查表**：产生任何"要不要加个功能 / 要不要换方案"的想法时，先问——① 它是否服务于"配置中心"这个定位？② 面试时它能否变成 5 分钟有深度的对话？③ 做完它是否会占用核心模块的时间？三条都通过才做。

## 二、总体打法：两线并行

项目成功的两个支柱缺一不可，**学习和开发必须同步推进**：

- **学习线（约 30% 时间）**：读 Raft 论文、读 braft / LevelDB / brpc 源码、写原理笔记。**这是"调库"与"懂库"的分水岭**。
- **开发线（约 70% 时间）**：按里程碑写代码、跑通、压测、记录数据。

每个里程碑都绑定四个产出：**代码 → 验收标准 → 简历素材 → 面试题**。防止"代码写完就结束，面试时讲不出来"。

## 三、技术学习路线（按里程碑展开）

### 阶段 0：环境与准备（M0，第 1 周）

**目标**：能在 Linux 环境编译运行 C++17 / brpc / braft / LevelDB。

**学习内容**：
- Linux 基础（文件、进程、端口、`ss`/`top`）、git 基本操作、Markdown。
- C++17 语法复习：智能指针、`std::thread`、`std::variant`、`std::optional`、RAII、移动语义、lambda、模板基础。
- CMake 基本语法：`add_executable`、`find_package`、`target_link_libraries`、`FetchContent`/vcpkg。

**⚠️ 实操关键（重要）**：brpc / braft **主要支持 Linux**，Windows 上编译支持不完整。你的开发机是 Windows，务必在 **WSL2（Ubuntu）或 Docker 容器**中开发，否则会卡在环境上浪费时间。推荐 Docker Desktop + 开发容器。

**验收**：`docker run` 一个 Ubuntu 容器能编译通过 hello-world + brpc 官方 example。

---

### 阶段 1：Raft 原理 + braft（贯穿 M1–M2，持续 2-3 周）

**这是整个项目最重要的知识投资。** 顺序：先懂 Raft，再用 braft，再读 braft 源码。

**学习路径**：
1. **Raft 论文**：《In Search of an Understandable Consensus Algorithm》(Ongaro & Ousterhout)，建议读中文翻译版，边读边对照交互演示。
2. **交互演示**：raft.github.io 动图，亲手模拟选举、日志复制，直到能预判下一步。
3. **braft 官方文档**（baidu.github.io/braft）：overview → server → client → cli → replication。
4. **braft 示例精读**：`example/counter/server.cpp` 与 `client.cpp`——理解 `StateMachine`、`node->apply`、`RouteTable`。
5. **braft 源码精读**（配合笔记，只读关键路径，不要逐行）：
   - `node.cpp`：Node 生命周期、`apply`、`commit`、`leader` 状态机
   - 选举：`election_timeout`、`pre_vote`、投票规则
   - 日志复制：`AppendEntries`、pipelining、`match_index`/`next_index`
   - `ReadIndex`：线性一致读的实现
   - `snapshot`：`on_snapshot_save/load`、`InstallSnapshot` 流程
   - 成员变更：`add_peer` / `remove_peer`

**产出（必须，放入 repo）**：`docs/raft-and-braft.md` —— 一份"Raft 原理 + braft 工程实现"笔记，用你自己的话写。**这是直接回应面试官"你是不是只会调库"的证据。**

**面试必会**：选举安全（同一任期一个 leader）、no-op 日志为什么需要、commit 规则、日志不一致如何处理、ReadIndex 步骤、快照与落后节点追赶。

---

### 阶段 2：LevelDB 与 LSM-Tree（M1 期间，1 周）

**学习路径**：
1. LSM-Tree 原理：写放大 / 读放大 / 空间放大，compaction 为什么存在。
2. LevelDB 源码结构（代码精炼，适合精读）：`memtable`、`sstable`、`log(WAL)`、`version`、`db_impl.cc`（compaction 与写路径）、`write_batch`。
3. 理解"为什么 LevelDB 单线程写"以及它如何与 Raft 串行 apply 匹配。

**产出**：`docs/leveldb-and-lsm.md` 笔记（重点：数据结构、写路径、compaction、调优参数如 block size / write buffer）。

**面试必会**：LevelDB 写流程、LSM 三种放大、compaction 触发条件、为什么选 LevelDB 而非 RocksDB/B+Tree。

---

### 阶段 3：brpc（M1 期间，3-5 天）

**学习内容**：bthread 线程模型（M:N、work-stealing）、协议栈（如何一个端口多协议）、内置服务（`/status` 监控、profiler）、同步/异步接口。

**产出**：`docs/brpc-notes.md` 简短笔记。

**面试必会**：bthread 与 pthread 的区别、brpc 为什么快（内存池、无锁队列、协议处理）、单端口多协议怎么实现。

---

### 阶段 4：工程与性能工具（M6–M7 使用）

- Docker Compose：编排 3 节点。
- GoogleTest：单元/集成测试。
- ghz（gRPC 压测）、wrk（HTTP 压测）：QPS、时延（P99）。
- Linux `perf` + 火焰图：定位 CPU 热点。
- GitHub Actions：自动构建、跑测试。

**产出**：每个工具的使用笔记 + 实测数据（压测报告、火焰图截图）。

## 四、开发路线图（里程碑 M0–M7）

> 每个里程碑：**目标 / 任务 / 验收标准 / 简历素材 / 面试题 / 预计耗时**（按每天 3-4 小时估算）。

### M0 环境与工程骨架 —— 0.5-1 周

- **任务**：Docker 开发容器；空工程 `CMakeLists.txt` 编译通过；README 初始化；git 仓库。
- **验收**：`cmake --build` 产出 hello 二进制；`git push` 首个 commit。
- **面试题**：CMake 基本概念；为什么用容器固定依赖版本。

### M1 单机 KV（brpc + LevelDB + Protobuf）—— 1-1.5 周

- **任务**：定义 `kv.proto`（Put/Get/Delete/Batch）；brpc Server 起 HTTP + gRPC 服务；LevelDB 封装 `Store` 类；实现单机 Put/Get。
- **验收**：curl 能写读；grpcurl 能调用 gRPC 接口；LevelDB 数据落盘重启可读。
- **简历素材**："统一 brpc 单端口提供 gRPC + HTTP 双协议接口"。
- **面试题**：LevelDB 写路径；protobuf 为什么高效；brpc 线程模型；HTTP 与 gRPC 差异。

### M2 接入 braft（3 节点复制 + 自动选主）—— 2-3 周（项目最关键的一步）

- **任务**：实现 `StateMachine`（`on_apply`/`on_snapshot_save/load`/`on_leader_start/stop`）；`node->apply` 提交写请求；`RouteTable` 客户端路由；本地 3 节点启动脚本；验证故障转移。
- **验收**：3 进程组成集群，写入 3 节点一致；kill Leader 后数秒内自动选主恢复；写请求在 Follower 上正确重定向。
- **简历素材**："基于 braft 实现 3 节点强一致配置存储，写路径经多数派提交，故障自动选主"。
- **面试题**（本里程碑最密集）：选举安全 / no-op / commit 规则 / 日志不一致处理 / 脑裂行为 / 快照。
- **注意**：本里程碑要**同步完成 braft 源码精读与 Raft 笔记**（阶段 1 产出）。

### M3 配置语义（MVCC + 版本 + 回滚 + Compaction）—— 2 周

- **任务**：引入全局 revision 与每 key version；`Publish`/`GetConfig(key, version)`/`Rollback`；存储结构设计（`config/{key}/` 多版本 + revision 索引）；Compaction 回收过期版本与 tombstone。
- **验收**：发布多版本后可查历史、可回滚；回滚产生新版本而非删除；连续写入后存储不无限膨胀。
- **简历素材**："设计并实现 MVCC 多版本模型与全局 revision，支持多版本发布、历史查询、一键回滚，并实现 Compaction 防止存储无限膨胀"。
- **面试题**：MVCC 与 revision 关系；为什么回滚产生新版本；Compaction 策略与代价；与 etcd 的对照。

### M4 Watch（长轮询 + 断点续传 + 背压）—— 1-1.5 周

- **任务**：HTTP 长轮询 `Watch(key, from_revision)`；事件缓冲；`on_apply` 产生事件唤醒挂起连接；慢消费者处理（背压/超时）。
- **验收**：客户端收到有序事件流；携带 revision 重连后不丢事件、不重复。
- **简历素材**："实现基于 HTTP 长轮询的 Watch 实时推送，以 revision 断点续传保证事件有序不丢"。
- **面试题**：为什么长轮询而非 gRPC 流/WebSocket（brpc 流控限制）；断点续传怎么实现；慢消费者怎么办；事件顺序怎么保证。

### M5 CAS 与线性一致读 —— 1 周

- **任务**：`CompareAndSwap` 作为专用 request 走 Raft，在 `on_apply` 串行比较-写入；读路径接入 braft ReadIndex；提供可选 `serializable` 降级读。
- **验收**：并发 CAS 只有一个成功且结果正确；发布后立即读必得新值（线性一致）。
- **简历素材**："CAS 原子更新基于 Raft 串行 apply；读路径用 ReadIndex 保证线性一致读，杜绝读到过期配置"。
- **面试题**：CAS 原子性来源；ReadIndex 的步骤与正确性（no-op 依赖）；Linearizable vs Serializable vs 顺序一致。

### M6 运维与发布（成员变更 + Docker 一键集群 + CI）—— 1 周

- **任务**：`AddPeer/RemovePeer`（配合快照追赶）；`/health`；Docker Compose 一键 3 节点；GitHub Actions 构建 + 测试。
- **验收**：`docker compose up` 一条命令起 3 节点；在线扩容新节点经快照追平；CI 绿。
- **简历素材**："Docker Compose 一键部署 3 节点集群；支持在线成员变更；GitHub Actions 持续集成"。
- **面试题**：成员变更的两种方式（单增删 / joint consensus）；扩容时为什么先要追数据；网络分区下成员变更行为。

### M7 测试、压测、混沌与优化 —— 1.5-2 周

- **任务**：GoogleTest 单元/集成；混沌脚本（kill Leader / kill Follower / 网络分区 / 重启）；ghz/wrk 压测；`perf` + 火焰图优化（找 1-2 个热点并优化，如序列化、批量写）。
- **验收**：混沌测试全程一致（写线性一致、Watch 有序不丢、集群自动恢复）；压测报告含 QPS 与 P99；优化前后对比数据。
- **简历素材**："混沌测试验证 kill Leader / 网络分区下自动选主与一致性；压测 P99 时延 XXms、QPS XXk；perf 火焰图定位并优化写路径热点"。
- **面试题**：怎么验证分布式系统正确性；压测指标怎么看；P99 比平均时延好在哪；做过的具体优化及收益。

## 五、面试支撑方案（贯穿全程，不可省略）

### 5.1 简历项目描述模板（里程碑全完成后使用）

```
Configraft —— 基于 Raft 的分布式配置中心（C++17 / braft / brpc / LevelDB）

- 基于百度工业级 Raft 库 braft 实现 3 节点强一致配置存储：写路径经多数派提交保证线性一致，
  读路径用 ReadIndex 避免读到过期配置，Leader 宕机数秒内自动选主恢复
- 设计并实现 MVCC 多版本模型与全局 revision，支持多版本发布、历史查询、一键回滚，
  并实现 Compaction 回收机制防止历史版本无限膨胀
- 实现基于 HTTP 长轮询的 Watch 实时变更推送，以 revision 断点续传保证事件有序不丢，含慢消费者背压处理
- 统一 brpc 单端口提供 gRPC + HTTP 双协议接口与内置监控；Docker Compose 一键部署 3 节点集群；
  支持在线成员变更；GitHub Actions 持续集成
- 混沌测试验证 kill Leader / 网络分区下的一致性；ghz/wrk 压测，P99 时延 XX ms，QPS XXk
```

### 5.2 面试 30 分钟讲解稿框架（背熟结构，内容用自己的话）

1. **0-2 分钟**：一句话定位 + 一句话演示（改限流阈值 → 实时推送 → 回滚）。
2. **2-10 分钟**：整体架构 + 一次请求的数据流（对着架构图讲，覆盖 brpc/braft/LevelDB 各在哪一步）。
3. **10-18 分钟**：两个深度模块任选——① MVCC + 版本回滚 + Compaction；② Watch 断点续传 + 背压。
4. **18-23 分钟**：一致性——Raft 写路径、ReadIndex 读路径、与 etcd 的对照。
5. **23-28 分钟**：工程——压测数据、混沌测试、你踩过的 2 个坑及解决。
6. **28-30 分钟**：反思与改进方向（诚实说出一个已知局限 + 改进方案）。

### 5.3 高频面试题清单（按里程碑分散自测）

- **C++/OS/网络**：智能指针与 RAII；`std::thread` 与原子操作；进程/线程/协程；TCP 三次握手与连接复用；select/epoll 区别。
- **存储**：LevelDB 写流程；LSM 三种放大；compaction 触发；为什么串行写不慢（batch）。
- **分布式**：Raft 选举安全；no-op 日志；commit 规则；日志不一致恢复；ReadIndex；快照；成员变更；脑裂/分区；线性一致 vs 顺序一致 vs 最终一致。
- **设计**：为什么配置中心要强一致；长轮询 vs 推送；版本回滚为什么不删历史；错误码与重试设计。

## 七、风险与避坑清单

| 风险 | 对策 |
|---|---|
| Windows 上编不过 brpc/braft | 用 WSL2 或 Docker 开发容器，**不要**在本机折腾编译（易劝退） |
| 依赖地狱（protobuf/brpc/braft 版本不匹配） | 全部依赖锁在 Docker 镜像内，用 vcpkg 固定版本 |
| 陷入自研 Raft 的冲动 | 项目边界明确"不写 Raft"；深度靠读 braft 源码 + 写笔记获得 |
| M2 卡住（Raft 概念最难） | 先用单进程多 raft 节点跑通官方 counter example，再迁移到多进程 |
| 只写代码不做笔记 | 笔记是"简历级证明"，每天固定 0.5h，M 结束时必须产出对应文档 |
| 功能越做越多、偏离定位 | 用第一节"防偏离检查表"把关，砍掉任何与配置中心无关的功能 |
| 面试前遗忘细节 | 每完成一个里程碑，用自己的话把"5.2 讲解稿"对应部分讲一遍并录音回听 |
| 卡壳求助路径 | 顺序：官方文档 → 官方 example → 相关博客/issue → 提问社区（先描述你已尝试的） |
