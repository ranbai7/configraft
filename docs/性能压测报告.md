> 2026-08-20 云服务器实测。本报告数据用于 README「性能与验证」章节及面试讲解。

## 4. 数据分析与结论

### 4.1 核心发现：Raft 复制规模代价（3 节点 → 5 节点）

**写路径吞吐随集群规模扩大而下降，读路径不受影响**——这是 Raft 多数派复制机制的直接体现：

| 写 Put | 3 节点 | 5 节点 | 下降 |
|---|---|---|---|
| c8 · 默认持久化 | 1814 | 1227 | **-32%** |
| c64 · 默认持久化 | 9854 | 7363 | -25% |
| c128 · 默认持久化 | 16013 | 12552 | -22% |
| c8 · 关 fsync | 15444 | 12430 | -20% |
| c64 · 关 fsync | 27096 | 22894 | -16% |
| HTTP POST · 默认 | 17121 | 12685 | -26% |

- **原因**：3 节点多数派 = 2/3（写需 2 个节点确认），5 节点多数派 = 3/5（需 3 个节点确认）。节点越多，Leader 需要同步日志给更多 Follower 并等多数派确认，**复制 + 确认开销线性增加**；P99 也随之升高（默认持久化下 c128 从 13.8ms → 18.7ms）。
- **读路径不变**（读走 Leader Lease 本地读，不涉及多数派确认）：Get c64 43-44k、HTTP GET 25-29 万，3/5 节点几乎一致。
- **容错权衡**：3 节点容忍 1 故障，5 节点容忍 2 故障——**用约 1/4 的写吞吐换取多一倍的故障容忍**，这是配置中心选型的核心权衡。

### 4.2 fsync 是写路径最大开销

无论 3 节点还是 5 节点，默认持久化 vs 关 fsync 在低并发下相差 **8-10 倍**（3 节点 c8：1.8k → 15.4k；5 节点 c8：1.2k → 12.4k）。这是"强一致 + 崩溃不丢已提交日志"的固有代价（`--raft_sync=false` 仅压测/演示用）。

### 4.3 c128 峰值确认

| 写 Put c64 → c128 | QPS 变化 | 结论 |
|---|---|---|
| 单机 | 39.4k → 40.4k（+2.6%） | 已饱和，单节点上限约 40k |
| 3 节点·默认 | 9.9k → 16.0k（+62%） | fsync 排队下更高并发仍能提升吞吐 |
| 3 节点·关 fsync | 27.1k → 29.4k（+8.5%） | 接近 8 核 CPU 上限 |
| 5 节点·关 fsync | 22.9k → 24.9k（+9%） | 接近 8 核 CPU 上限 |

- **单机写上限约 40k QPS**（c64 即饱和，受单进程 CPU 限制）；
- **集群写在高并发下受 8 核 CPU 上限约束**（关 fsync 时 c128 ≈ 29k @3 节点 / 25k @5 节点）。

### 4.4 读远高于写（符合配置中心形态）

HTTP 读 GET 25-29 万 QPS，写路径 1.2k–29k——**读比写高 10~100 倍**，完全匹配配置中心"读多写少"的业务场景（服务启动/变更时拉配置，配置发布低频）。

## 6. 审查加固后复测（2026-08-20，锁开销验证）

> **背景**：2026-08-20 全项目代码审查（commit e5d737b）为 Store 引入共享互斥量（`db_mu_`，保护快照重建与并发读）并为单机模式写路径加互斥锁。需**同环境复测**确认锁开销。

**测试环境**：与第 1 节相同（8 核阿里云主机，`configraft_server` md5=`bfb2245726aeaf46f3804a53d95bc215`，为加锁后最新代码构建产物）。命令 `bash scripts/benchmark.sh --all --dur 10`。

### 6.1 3 节点集群对比（加锁前 vs 加锁后）

| 场景 | 加锁前 | 加锁后 | 差异 |
|---|---|---|---|
| gRPC Put c8 · 默认持久化 | 1.8k / 9.1ms | 1806 / 10.31ms | ≈0% |
| gRPC Put c64 · 默认持久化 | 9.9k / 11.9ms | 9951 / 11.55ms | ≈0% |
| gRPC Put c128 · 默认持久化 | 16.0k / 13.8ms | 15958 / 13.04ms | ≈0% |
| gRPC Put c8 · 关 fsync | 15.4k / 1.4ms | 15883 / 1.44ms | +3% |
| gRPC Put c64 · 关 fsync | 27.1k / 5.0ms | 28179 / 4.65ms | +4% |
| gRPC Put c128 · 关 fsync | 29.4k / 7.8ms | 30969 / 7.10ms | +5% |
| gRPC Get c64 · 默认持久化 | 44.2k / 2.9ms | 45245 / 2.84ms | +2% |
| HTTP 读 GET | 275k / 0.50ms | 274801 / 0.48ms | ≈0% |
| HTTP 写 POST · 默认持久化 | 17.1k / 12.5ms | 17947 / 12.57ms | +5% |
| HTTP 写 POST · 关 fsync | 70.7k / 4.5ms | 75378 / 4.24ms | +7% |

### 6.2 结论

- **锁开销可忽略**：集群写路径 QPS 差异全部在 **±5% 内**（多数持平或轻微提升，属测量噪音），读路径（Leader Lease 本地读）完全不受影响。
- **共享锁换 UAF 修复零性能代价**：`shared_mutex` 每次读写仅多一次锁操作（纳秒级原子操作），相对 LevelDB IO 与 Raft 复制可忽略。
- **单机模式个别 P99 异常**（如 fsync=true 下 HTTP POST P99=81ms）系单机同机压测时 CPU 资源竞争噪音，fsync=false 时同项恢复 47ms；不影响集群结论。
