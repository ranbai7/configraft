# Configraft 运行演示脚本（配置中心业务视角）

> 对齐 `docs/面试准备.md` 第 2 节"30 分钟讲解稿"。本项目是**分布式配置中心**，演示时不要按"KV 功能清单"逐项过一遍（那看起来像一个 KV 玩具），而应围绕微服务配置管理的**痛点 → 解法**讲一个完整故事，让每个功能都落到业务场景上。
> 全部命令已在 3 节点集群上实测可用（2026-08-17）。

## 一句话定位

微服务配置的四大痛点：**配置散落各机器、改完必须重启才生效、改错没法快速恢复、配置中心自己会挂**。Configraft 用 Raft 强一致 + MVCC 版本化 + Watch 实时推送解决全部四点。

演示主线：**发布 → 实时生效 → 变更版本化 → 回滚 → 容灾**（可选加演：CAS 并发治理）。

## 图形化演示：Web Dashboard（推荐，效果最直观）

启动集群后，浏览器打开**任意节点**即可访问可视化管理界面：

```
http://127.0.0.1:8001/dashboard      （或 8002 / 8003）
```

页面 4 个区域：

| 区域 | 内容 | 演示要点 |
|---|---|---|
| 集群节点 | 3 节点卡片：角色/term/commit/applied，leader 金色高亮，离线标红（2s 轮询） | 写操作时各节点 commit/applied 同步递增；kill leader 后节点标红 → 新 leader 自动高亮 |
| 配置/KV 操作 | Put / Get / Delete / CAS + Publish / GetConfig / 回滚，写请求**自动打到 leader** | 输入 key/value 点按钮即可完成操作，无需记 curl 命令 |
| 操作结果 | 响应 JSON + 配置版本链 | 回滚后版本链直观展示"新版本 + 旧版本保留" |
| 实时变更流 | Watch 长轮询监听**所有 key**，revision 递增滚动，PUT 绿 / DELETE 红 | **核心亮点**：页面上任何写操作、或终端里的写入，都实时出现在右侧事件流 |

**推荐演示流程**（录屏效果最佳）：
1. 打开 Dashboard → 展示 3 节点在线、leader 金色高亮；
2. 操作面板发布 `gateway.rate_limit=2000` → 右侧 Watch 流实时弹出 PUT 事件；
3. 连续 Publish 两次 → Watch 流 revision 递增；点"配置 + 历史"看版本链；
4. 点"一键回滚"到 v1 → Watch 流再弹 PUT，结果区显示新版本号；
5. 终端 `kill -9` 当前 leader → 页面节点卡片变红离线，约 4 秒后新 leader 金色高亮、配置仍可读（容灾可视化）。

> 实现说明：后端 `src/server/dashboard_service_impl.{h,cpp}` 以 `--web_dir`（默认 `web/`，相对启动 cwd）托管静态文件；
> 前端 `web/` 为纯原生 HTML/CSS/JS（无框架、无构建工具）；Dashboard 页面与 leader 之间跨端口请求由各 service 的
> CORS 响应头支持（`src/server/rest_util.h` `HandleCorsPreflight`）。静态资源服务路径为 `/dashboard`，
> 根路径 `/` 被 brpc 内置 IndexService 占用，无法替代。

## 0. 前置准备（一次性）

```bash
cd configraft
cmake --build build -j4
bash scripts/run_cluster.sh                 # 3 节点集群，端口 8001-8003

# 动态定位 leader（写请求必须打 leader）
L=$(for i in 1 2 3; do curl -s 127.0.0.1:800$i/healthz \
      | grep -q '"role":"leader"' && echo 800$i && break; done)
echo "leader=$L"
```

后续命令中的 `$L` 即当前 leader 端口。

## 1. 场景一：集中管理 + 多副本强一致（解决"配置散落、各节点不一致"）

**讲解词**：传统方式配置散落在各服务本地文件/环境变量里，改一处要逐台登录修改，容易改漏、各节点版本漂移。这里一份配置写入集群，**三个节点同时生效**。

```bash
# 发布配置
curl -X POST http://127.0.0.1:$L/v1/config/gateway.rate_limit -d '{"value":"2000"}'

# 在 leader 和两个 follower 上分别读，返回完全一致
curl http://127.0.0.1:$L/v1/config/gateway.rate_limit
curl http://127.0.0.1:8001/v1/config/gateway.rate_limit
curl http://127.0.0.1:8002/v1/config/gateway.rate_limit
```

**观众观察点**：三个节点返回相同的 value 和 revision。强调读是**线性一致读**（Follower 不读本地过期数据）——可补演示：把写请求打到 follower，会返回 `not leader, leader=...` 重定向，这本身就是一致性的证明。

```bash
curl -X POST http://127.0.0.1:8001/v1/kv/try_follower -d '{"value":"x"}'
# {"code":3,"message":"not leader, leader=127.0.0.1:800X:0"}
```

## 2. 场景二：Watch 实时生效（解决"改配置要重启服务"）—— ⭐ 核心卖点

**讲解词**：微服务最常见的痛点——改个配置要发布、重启、再发布、再重启，停机窗口大。Configraft 提供 HTTP 长轮询 Watch：**配置一变，所有订阅方零延迟收到新值，无需重启**。

```bash
# 终端 A：模拟订阅方，对 key 发起长轮询（挂起等待）
curl "http://127.0.0.1:$L/v1/watch?key=gateway.feature_flag&from_revision=0&timeout_ms=30000"

# 终端 B：触发变更
curl -X POST http://127.0.0.1:$L/v1/kv/gateway.feature_flag -d '{"value":"on"}'
```

**观众观察点**：终端 A 的 curl **瞬间返回**：

```json
{"current_revision":N,"events":[{"revision":N,"key":"gateway.feature_flag","value":"on","type":"PUT"}]}
```

**讲解词**：事件带全局 `revision`（逻辑时钟），是 Watch/MVCC/CAS 的共同锚点。服务收到事件即可加载新配置——**不重启、不停机**，这正是"配置中心"区别于普通 KV 的地方。

**断点续传（进阶）**：订阅方拿到 `current_revision` 后，下次用 `from_revision=N` 继续监听，**只会收到 N 之后的新事件**，不丢不重：

```bash
# 终端 A：用刚才返回的 current_revision=N 继续监听
curl "http://127.0.0.1:$L/v1/watch?key=gateway.feature_flag&from_revision=N&timeout_ms=30000"
# 终端 B：再次变更
curl -X POST http://127.0.0.1:$L/v1/kv/gateway.feature_flag -d '{"value":"off"}'
# 终端 A 只收到新事件（revision > N）
```

## 3. 场景三：多版本 + 一键回滚（解决"改错配置没法快速恢复"）

**讲解词**：生产事故常见场景——上线把限流阈值从 2000 改成 8000，结果打爆下游。传统方式要查哪个机器改的、改回多少。这里每次发布自动保留历史版本，**一条命令回滚到任意版本**。

```bash
# 连续发布 v2、v3
curl -X POST http://127.0.0.1:$L/v1/config/gateway.rate_limit -d '{"value":"8000"}'
curl -X POST http://127.0.0.1:$L/v1/config/gateway.rate_limit -d '{"value":"12000"}'

# 查看版本链（history 返回 v1 → v2 → v3）
curl "http://127.0.0.1:$L/v1/config/gateway.rate_limit"

# 事故复盘：一键回滚到 v1
curl -X POST http://127.0.0.1:$L/v1/config/gateway.rate_limit/rollback -d '{"target_version":1}'

# 验证已恢复
curl http://127.0.0.1:$L/v1/config/gateway.rate_limit
```

**观众观察点**：回滚后 value 回到 `2000`，且 history 里旧版本仍在（回滚**不删历史**、而是"写回旧值产生新版本"，对齐 etcd 语义，因 Raft 日志 append-only，可全量追溯）。

## 4. 场景四：容灾（解决"配置中心自己挂了"）—— ⭐ 展示 Raft 价值

**讲解词**：配置中心是基础设施，自己绝不能是单点。杀掉 leader，集群**数秒内自动选主**，配置不丢、服务不断。

```bash
# 重新定位当前 leader（不依赖前面的 $L，独立可跑）
L=$(for i in 1 2 3; do curl -s 127.0.0.1:800$i/healthz \
      | grep -q '"role":"leader"' && echo 800$i && break; done)
echo "leader=$L"

# 找出 leader 进程，模拟宕机（kill -9）
LPID=$(ss -tlnp 2>/dev/null | grep ":$L " | grep -oP 'pid=\K[0-9]+')
kill -9 $LPID

# 等待重新选主，重新定位新 leader
sleep 4
NEWL=$(for i in 1 2 3; do curl -s 127.0.0.1:800$i/healthz \
        | grep -q '"role":"leader"' && echo 800$i && break; done)
echo "新 leader=$NEWL"

# 关键验证：宕机前发布的配置在新 leader 上完好无损
curl http://127.0.0.1:$NEWL/v1/config/gateway.rate_limit
```

**讲解词**（三个可讲的 Raft 知识点）：
- 数据不丢 = **Raft 多数派复制**：写入要多数节点确认才返回成功，所以任何单点宕机都不丢已提交配置；
- 自动选主 = **Leader Election**：follower 超时后发起选举，term 递增；
- Follower 强一致读不读过期数据 = **Leader Lease + ReadIndex**：读请求重定向到 leader，杜绝"读到旧配置"。

## 5. 场景五（可选加分）：CAS 安全发布（解决"多人并发改配置互相覆盖"）

```bash
# 同学 A：认为当前值是 5000，改成 8000 —— 成功
curl -X POST http://127.0.0.1:$L/v1/kv/gateway.rate_limit/cas -d '{"expect":"5000","value":"8000"}'
# 同学 B：也认为当前值是 5000，改成 10000 —— 期望不匹配，被原子拒绝
curl -X POST http://127.0.0.1:$L/v1/kv/gateway.rate_limit/cas -d '{"expect":"5000","value":"10000"}'
# 读取确认：最终是 8000，B 的覆盖被挡下
curl http://127.0.0.1:$L/v1/kv/gateway.rate_limit
```

**讲解词**：CAS 走 Raft 串行 apply，**天然原子**——并发 CAS 恰好一个成功（有单节点 braft 组测试 `tests/raft_cas_test.cpp` 验证）。适合多团队改同一配置项的治理场景。

## 7. 演示避坑清单

1. **写请求必须打 leader**：打 follower 会返回 `not leader` 重定向（这是强一致设计，不是故障），但演示前务必用第 0 节的命令定位 leader。
2. **配置版本只来自 Publish/Rollback**：普通 KV 写（`/v1/kv/` 的 Put/CAS）**不产生配置历史版本**，只有 `/v1/config/` 的 Publish 才写 `cfg/{key}/{ver}` 索引。场景三请用 Publish 接口，`GetConfig(version)` / `Rollback` 只能操作 Publish 产生的版本。
3. **进程清理 / 停止集群**：推荐直接 `bash scripts/run_cluster.sh stop`（一条命令，内部用 `pgrep -x configraft_serv` 精确匹配被内核截断为 15 字符的进程名，自动清理）。等价手动写法：
   ```bash
   for pid in $(pgrep -x configraft_serv); do kill "$pid"; done
   ```
   ⚠️ 不要用 `pgrep -f "configraft_server"`——在 Claude Code 等环境会误匹配 shell wrapper。
4. **节点数据目录**：`run_cluster.sh` 每次启动会清空 `/tmp/cfg-cluster`，保证从干净状态开始；手动重启某节点时保持 `--data_dir` 不变即可恢复旧数据。

## 8. 附录：完整命令速查

```bash
# ---- 健康检查 / 状态 ----
curl http://127.0.0.1:$L/healthz          # role/term/commit/applied/peers
curl http://127.0.0.1:$L/status           # brpc 监控面板：各方法 QPS/延迟

# ---- KV（/v1/kv/*）----
curl -X POST http://127.0.0.1:$L/v1/kv/{key} -d '{"value":"v"}'        # Put
curl http://127.0.0.1:$L/v1/kv/{key}                                    # Get（线性一致）
curl -X DELETE http://127.0.0.1:$L/v1/kv/{key}                          # Delete
curl -X POST http://127.0.0.1:$L/v1/kv/batch \
  -d '{"entries":[{"key":"a","value":"1"},{"key":"b","value":"2"}]}'    # BatchPut
curl -X POST http://127.0.0.1:$L/v1/kv/{key}/cas \
  -d '{"expect":"old","value":"new"}'                                    # CompareAndSwap

# ---- 配置（/v1/config/*）----
curl -X POST http://127.0.0.1:$L/v1/config/{key} -d '{"value":"v"}'     # Publish（递增版本）
curl "http://127.0.0.1:$L/v1/config/{key}"                              # GetConfig 最新（含 history）
curl "http://127.0.0.1:$L/v1/config/{key}?version=N"                    # 读指定配置版本
curl -X POST http://127.0.0.1:$L/v1/config/{key}/rollback \
  -d '{"target_version":N}'                                             # 回滚（写回旧值，产生新版本）

# ---- Watch（HTTP 长轮询）----
curl "http://127.0.0.1:$L/v1/watch?key={key}&from_revision=0&timeout_ms=30000"

# ---- Admin（仅 HTTP；gRPC 不可用，见下）----
curl http://127.0.0.1:$L/healthz                                          # GetHealth
curl -X POST http://127.0.0.1:$L/addpeer -d '{"peer":"127.0.0.1:8004"}'   # AddPeer
curl -X POST http://127.0.0.1:$L/removepeer -d '{"peer":"127.0.0.1:8001"}'# RemovePeer

# ---- gRPC（configraft_client）----
./build/configraft_client --server 127.0.0.1:$L --method Put  --key k --value v
./build/configraft_client --server 127.0.0.1:$L --method Get  --key k
./build/configraft_client --server 127.0.0.1:$L --method CAS  --key k --expect v --value v2

# ---- 单元测试 ----
ctest --test-dir build          # store_test / raft_cas_test / watch_test
```

> **已知限制**：`configraft.v1.AdminService` 的 gRPC 方法（`GetHealth/AddPeer/RemovePeer`）会返回 `Unimplemented`——因为 brpc 的 `restful_mappings` 将具体方法名映射到 HTTP 路径（`/healthz` 等）后，该方法的普通 RPC 路径即被占用（见 `src/server/server.cpp` `kAdminServiceRestMappings` 注释）。Admin 接口设计为**仅走 HTTP**，不影响业务功能；KV/Config/Watch 的 gRPC 均正常。
