# 面试准备：简历描述 + 讲解稿 + 高频题

> 对齐 `docs/开发计划.md` 第五节"面试支撑方案"。项目已完成（M0–M7），此文档用于背熟讲稿、自测高频题。

## 1. 简历项目描述（一段话，写在"项目经历"）

```
Configraft —— 基于 Raft 的分布式配置中心（C++17 / braft / brpc / LevelDB）

- 基于百度工业级 Raft 库 braft 实现 3 节点强一致配置存储：写路径经多数派提交，读路径用 leader lease 保证线性一致（避免读到过期配置），Leader 宕机数秒内自动选主恢复
- 设计并实现 MVCC 多版本模型与全局 revision，支持多版本发布、历史查询、一键回滚，并实现 Compaction 回收防止历史版本无限膨胀
- 实现基于 HTTP 长轮询的 Watch 实时变更推送，以 revision 断点续传保证事件有序不丢，含慢消费者背压处理；CAS 原子更新基于 Raft 串行 apply
- 统一 brpc 单端口提供 gRPC + HTTP 双协议；支持在线成员变更（新节点快照追赶后进配置）；Docker Compose 一键部署 3 节点；GitHub Actions 持续集成
- 混沌测试验证 kill Leader / 网络分区下的一致性（写线性一致、Watch 有序不丢、自动恢复）；压测集群写 QPS ~2.9k、P99 5ms，定位并修复 3 个高并发缺陷
```

## 2. 30 分钟讲解稿框架（背熟结构，内容用自己的话）

1. **0–2 分钟**：一句话定位 + 一句话演示（改限流阈值 → Watch 实时推送 → 回滚）。
2. **2–10 分钟**：整体架构 + 一次请求的数据流（对着架构图：brpc 收到请求 → Raft 提交复制日志 → on_apply 串行写 LevelDB → Broadcast Watch 事件 → 返回）。
3. **10–18 分钟**：两个深度模块任选——① MVCC + 版本回滚 + Compaction；② Watch 断点续传 + 背压 + 追赶节点修复。
4. **18–23 分钟**：一致性——Raft 写路径、leader lease 读路径、CAS 原子性、与 etcd 对照。
5. **23–28 分钟**：工程——压测数据、混沌测试方法、踩过的 3 个坑（std::cv 占 worker 假死 / Apply closure UAF / Watch 追赶节点重播）。
6. **28–30 分钟**：反思——已知局限（fsync 与持久性权衡、leader lease 就绪窗口）+ 改进方向（批量 fsync、ReadIndex 迁移）。

## 3. 高频面试题自测清单

### 一致性（最深，必考）
- Raft 选举安全 / no-op 日志作用 / commit 规则 / 日志不一致恢复
- 为什么"发布后立即读必得新值"（leader lease 的正确性承重墙）
- Linearizable vs Serializable vs 顺序一致
- CAS 原子性来源；失败为什么不消耗 revision

### Watch / MVCC
- 断点续传怎么实现（revision 锚点）？不丢不重怎么保证？
- 慢消费者怎么办（背压 overflow）？落后节点重播旧事件怎么修？
- 回滚为什么不删历史？Compaction 策略与代价？

### 成员变更 / 运维
- 成员变更两种方式（单增删 / joint consensus）？扩容为什么先追数据？
- 网络分区下成员变更行为？
- Docker Compose 一键部署的坑（固定 IP、镜像源、/healthz 冲突）

### 工程 / 压测
- 怎么验证分布式系统正确性（混沌测试方法）？
- P99 比平均时延好在哪？压测指标怎么解读？
- 做过的具体优化及收益（fsync 热点 2.2 倍、std::cv 假死修复）
- fsync 与 Raft 持久性的权衡

### C++ / 存储
- 智能指针与 RAII；bthread 与 pthread 的区别
- LevelDB 写流程 / LSM 三种放大 / compaction 触发
- 为什么 LevelDB 单线程写与 Raft 串行 apply 匹配
