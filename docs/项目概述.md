## 〇、审查意见摘要（原方案 → 重构决策）

| # | 原方案 | 问题 | 重构决策 |
|---|--------|------|----------|
| 1 | 同时引入 **brpc**（Raft 内部）+ **gRPC(C++)**（对外 RPC）+ **cpp-httplib**（对外 HTTP）三套网络框架 | brpc 在**同一端口**已内置 gRPC（Serve gRPC）与 RESTful HTTP 协议及内置监控/调试服务；三套框架冗余，构建复杂、protobuf 版本易冲突、代码重复 | **统一 brpc 为唯一网络框架**：Raft 内部通信、对外 gRPC（unary）、对外 HTTP 全部基于 brpc；对外协议仍为 gRPC + HTTP，标准 gRPC 客户端（grpcurl / ghz / 跨语言 SDK）可直接访问 |
| 2 | Watch 机制"基于**长轮询或 gRPC 流式推送**"二选一含糊 | brpc 作为 gRPC server 时服务端流式存在窗口更新限制（客户端未确认数据 1MB、窗口更新触发条件），多连接场景有死锁风险；两套实现工作量翻倍 | Watch **明确采用 HTTP 长轮询**（Consul / etcd v2 同款成熟方案），配合全局 revision 做断点续传与增量同步；对外另提供 gRPC unary 的查询接口 |
| 3 | 多版本发布 + 历史查询，但**无版本回收机制** | 历史版本无限累积 → LevelDB 无限膨胀、磁盘耗尽、写放大 | 引入**全局单调 revision + MVCC**（类 etcd），并实现 **Compaction / 版本保留策略**（保留最近 N 个版本 + 回收删除 tombstone） |
| 4 | 未定义**读一致性** | 配置中心要求"发布即生效"，读若不线性一致会读到旧值 | 明确读路径：**默认线性一致读（braft ReadIndex）**；写必经 Leader |
| 5 | "Leader 失效后 **30 秒内**恢复服务" | 恢复耗时取决于选举超时等配置，是**可配置项**而非固定值 | 改为"选举超时可配置（示例 1000ms），Leader 宕机后数秒内自动完成选主恢复" |
| 6 | CAS 原子更新，但未说明正确性依据 | CAS 正确性依赖"单 Leader + 状态机串行 apply"，不说明则面试一问就破 | 说明 CAS 作为**专用请求类型**提交 Raft，在 `on_apply` 中串行完成"比较-写入"，天然原子 |
| 7 | LevelDB 作存储引擎 | 有人会质疑 LevelDB 单线程写是瓶颈 | 反向论证：LevelDB 串行写与 Raft **串行 apply 天然匹配**；且 LevelDB 代码精炼，便于面试讲清 LSM-Tree 与性能调优 |
| 8 | 未提**快照（Snapshot）**机制 | braft 强制要求实现 `on_snapshot_save/load`，否则日志无限增长且落后节点无法追赶 | 补充快照模块：LevelDB 导出 + braft SnapshotStorage，与日志压缩、节点追赶关联 |
| 9 | 未提**客户端 Leader 路由** | 写请求必须到达 Leader；客户端不知道该找谁 | 明确：客户端通过 braft `RouteTable` 获取/跟踪 Leader；写入非 Leader 时返回重定向或转发 |
| 10 | 压测工具 ghz / wrk | 统一 brpc 后需与对外协议对应 | 保留：ghz 压 gRPC（brpc 兼容 gRPC 协议）、wrk 压 HTTP；另用 brpc 内嵌监控面板观察时延/QPS |
| 11 | 无**故障注入/一致性验证** | 面向面试的项目若只有功能、无故障演练，说服力弱 | 新增混沌测试：kill Leader、网络分区、节点重启、成员变更演练；对比 Jepsen 思路验证"写线性一致、Watch 有序" |
| 12 | 依赖环境易踩坑（brpc/braft/protobuf 版本） | 本机编译 brpc/braft 常见"依赖地狱" | Docker 多阶段构建固化构建环境；CI 里预置可复现的编译与测试 |

**结论**：原方案的技术底座（braft + LevelDB + brpc 系）方向正确、真实可信，与百度 braft 在百度内部构建 KV/SQL/元数据系统的实践一致；主要问题在**网络框架冗余、Watch 方案含糊、缺少版本回收与一致性语义定义**。以上为全部改动点。

## 一、项目定位

**Configraft** 是一个轻量级、强一致（线性一致）的分布式键值存储系统，对外以 **分布式配置中心** 形态提供能力。以百度 braft（工业级 C++ Raft）为共识底座，LevelDB 为单机存储引擎，brpc 为统一网络框架，提供 gRPC 与 HTTP 双协议接口。

一句话定位：**"C++ 版的 etcd 子集"**——集中管理、实时生效、强一致、可回滚的配置服务，面向微服务架构。

## 二、核心架构

```
┌───────────────────────────────────────────────────────────────┐
│                      客户端 / SDK（跨语言）                      │
│    gRPC(HTTP/2, unary)    HTTP(RESTful)    HTTP(长轮询 Watch)   │
└───────────────┬───────────────────────────────────────────────┘
                │             brpc 单端口多协议
┌───────────────▼───────────────────────────────────────────────┐
│              API / 服务层（brpc Server）                        │
│   KVService    ConfigService    WatchService    AdminService   │
│   (Put/Get/…)   (Publish/Rollback)(事件推送)    (成员/健康检查)   │
└───────────────┬───────────────────────────────────────────────┘
┌───────────────▼───────────────────────────────────────────────┐
│              Raft 层（braft）                                  │
│   选主 / 日志复制 / ReadIndex / 成员变更 / Snapshot / 故障转移    │
└───────────────┬───────────────────────────────────────────────┘
┌───────────────▼───────────────────────────────────────────────┐
│              复制状态机 ReplicatedStateMachine                 │
│   on_apply（串行）：MVCC 写入 · 版本管理 · CAS · Watch 事件 · Compaction │
└───────────────┬───────────────────────────────────────────────┘
┌───────────────▼───────────────────────────────────────────────┐
│              存储层（LevelDB，单节点一份）                       │
│   KV 数据（MVCC 多版本） · revision 索引 · 墓碑/回收 · Raft 元数据 │
└───────────────────────────────────────────────────────────────┘
```

**写路径**：客户端 → Leader API → `node->apply(task)` 提交日志 → 多数派确认并写 WAL → commit → `on_apply` 串行写入 LevelDB（产生新 revision 与 Watch 事件）→ 返回客户端。

**读路径（线性一致）**：客户端 → Leader API → braft ReadIndex 确认读位置 → 从本地状态机读取 → 返回。杜绝读到过期数据。

**Watch 路径**：客户端发起 HTTP 长轮询并携带上次收到的 revision → 挂起在事件缓冲上 → `on_apply` 产生事件后立即唤醒推送 → 客户端用新 revision 再次请求，实现增量同步与断点续传。

## 四、核心模块设计

### 1. API / 服务层（brpc）
- **KVService**：`Put / Get / Delete / BatchPut / CAS`（gRPC + HTTP 双协议）。
- **ConfigService**：`Publish(key, value)`（自动递增版本）、`GetConfig(key, version)`、`Rollback(key, target_version)`。
- **WatchService**：HTTP 长轮询 `Watch(key, from_revision)`，返回事件序列 + 最新 revision。
- **AdminService**：`GetHealth`（节点角色/状态/raft 详情）、`AddPeer / RemovePeer`（成员变更）。

### 2. Raft 层（braft）
- 复用 braft 全部能力：选主、日志复制、管道复制、ReadIndex 线性一致读、成员变更、Snapshot。
- 写请求经 `node->apply(task)` 进入复制日志；**状态只在 `on_apply` 中修改**，保证多副本一致。
- 客户端经 `braft::RouteTable` 发现与跟踪 Leader；写入落在 Follower 时返回重定向提示。

### 3. 复制状态机（本项目的核心工作量，也是面试主战场）
- **MVCC 数据模型**（参考 etcd v3）：
  - 全局单调 `revision`：每次写操作递增，作为逻辑时钟与 Watch 断点锚点；
  - 每 key 的 `version`：该 key 的修改序号，供 `Publish`/`GetConfig`/`Rollback` 使用；
  - 存储 key 组织：`config/{key}/` 下的多版本记录 + 全局 revision 索引。
- **CAS**：`CompareAndSwap` 作为专用 request 类型提交 Raft，在 `on_apply` 串行比较-写入，天然原子，无需额外锁。
- **Watch 事件**：`on_apply` 产生事件后写入事件缓冲，唤醒挂起的长轮询连接。
- **Compaction**：定时/按大小回收已过期的历史版本与 tombstone，防止存储无限膨胀。

### 4. 存储层（LevelDB）
- 每节点一份 LevelDB：持久化 MVCC 数据与元数据。
- LevelDB 的 Snapshot 接口与 braft 快照导出配合，实现 `on_snapshot_save / on_snapshot_load`。
- 崩溃恢复：Raft 日志重放 + 最近快照加载，无需额外 WAL（braft 自带日志持久化）。

### 5. 快照与恢复
- 日志无界增长时由 braft 触发快照：将状态机整体导出到 SnapshotStorage；
- 落后节点通过 InstallSnapshot 追赶，快速追平后继续日志复制；
- 节点重启：加载最近快照 + 重放其后日志。

### 6. 客户端路由与一致性读
- 写：只允许 Leader；非 Leader 收到写请求返回"重定向到 Leader"（etcd 同款语义）。
- 读：默认走 Leader + ReadIndex（线性一致）；可配置降级为 Follower 本地读（`serializable`，监控等非关键场景）。

## 五、数据模型与版本模型

```
配置项 key:            "gateway.rate_limit"
多版本（version 递增）:  v1=1000 → v2=2000 → v3=1500
全局 revision:         42 → 43 → 44 （每次写全局递增）
Watch 锚点:            from_revision = 43  → 收到 v3 的变更事件
Rollback:             Rollback("gateway.rate_limit", 2) → 恢复到 v2=2000，产生新版本 v4=2000
```

- 回滚**不删除历史**，而是写回旧值并产生新版本（与 etcd 语义一致），历史始终可查。
- 版本保留：默认保留每 key 最近 N 个版本（如 10 个）与最近 T 时间，Compaction 回收更早数据。

## 六、一致性语义（面试重点，务必能讲清）

| 操作 | 一致性 | 实现 |
|------|--------|------|
| Put / Delete / Batch / CAS / Publish / Rollback | **线性一致** | 全部经 Raft 多数派确认后 apply |
| Get（默认） | **线性一致** | Leader + ReadIndex |
| Get（可选 `serializable`） | 可容忍轻微过期 | Follower 本地读，用于监控 |
| Watch | **有序、不丢**（可断点续传） | 事件来自 Raft apply 序列，按 revision 排序 |

## 七、容错与运维

- **3 节点集群，容忍 1 节点宕机**；选举超时可配置（示例 1000ms），Leader 宕机后数秒内自动选主，期间写短暂不可用、读（线性一致）短暂不可用。
- **成员变更**：`AddPeer / RemovePeer` 在线动态扩缩容，新节点经快照追赶后加入。
- **健康检查**：`GET /health` 返回节点角色、commit/apply index、磁盘状态；brpc 内置监控面板展示 QPS、时延、bthread 状态。

## 八、实施路线图（可落地、分里程碑）

| 里程碑 | 内容 | 验收标准 |
|--------|------|----------|
| **M1 单机跑通** | 工程骨架（CMake + brpc + LevelDB + Protobuf）；单节点 KV Put/Get | 本机编译通过，curl 可写读 |

## 九、测试与验证策略

- **单元测试**（GoogleTest）：MVCC、版本回滚、CAS、Compaction 边界。
- **集成测试**：3 节点 Docker 集群上的功能全链路。
- **混沌/故障演练**：kill Leader、kill Follower、网络分区、节点重启后验证"写线性一致、读一致、Watch 有序不丢、集群自动恢复"。
- **性能测试**：ghz / wrk 输出 QPS 与 P99；对比单写线程与批量（BatchTx 思路）的效果。

## 十、面试可讲解的技术深度点（按含金量排序）

1. Raft 原理与 braft 工程实现：选主、日志复制、提交语义、ReadIndex、Snapshot。
2. MVCC 与 Compaction：为什么配置中心需要多版本、如何防止存储膨胀（对齐 etcd 设计）。
3. Watch 的技术取舍：为什么长轮询而非 gRPC 流（brpc 流控限制、配置中心场景、断点续传）。
4. brpc 单端口多协议：统一框架如何降低成本，以及它的限流/流控边界。
5. 一致性读的两难：Linearizable vs Serializable，ReadIndex 的正确实现（no-op 日志等坑）。
6. LevelDB：LSM-Tree 写放大/读放大、为何与 Raft 串行 apply 匹配。
7. 故障演练方法论：如何用混沌测试证明分布式系统正确。
